# Aivara board card delivery

## When to Use

A look — an operator wake naming a card on aivara-se project 2 (the Development board) — assigns you a build. Carry that one card from Refined to an open, gate-green PR; one run per look, no second card.

When the operator hands a frozen spec prompt instead — the repository's documents are the specification, board writes are forbidden — it is the same loop without the card: see `references/frozen-spec-delivery.md`, and loop steps 7 and 8 do not apply. The same reference covers the inverse assignment: a design change already merged, and the code to be brought up to it with the documents untouched.

## The loop

1. Read the live state, never the prompt's snapshot: `gh project item-list 2 --owner aivara-se --format json` (status + assignees), the card via `gh api repos/aivara-se/dispatcher/issues/<n>` (porcelain `gh issue view` can print nothing and exit 0), and the repo at `~/github/aivara-se/dispatcher` after `git pull --ff-only`.
2. Read `AGENTS.md`, `docs/PRODUCT.md`, `docs/SYSTEMS.md`, every ADR the card touches, and the org skills at `~/github/aivara-se/.agents/skills/{coding,testing,writing}/SKILL.md` before writing code.
3. The card's *Frozen surface* section is the contract: `go doc -all ./internal/<pkg>` must show nothing beyond it. Readings the card leaves open go in a PR body section named for them — never chosen in silence.
4. Parallel cards own sibling packages (check `gh pr list` for open branches before writing); touch only what the card lists.
5. Gate before pushing, each command read: `gofmt -l .` (empty is the pass), `go vet ./...`, `go test ./...`. Prove every commit green on its own tree (`git worktree add`). For a binary, also boot it by hand: scratch config under `/root/scratch` (never `/tmp`, noexec), curl the port, SIGTERM, check exit code and files. For a package that calls an outside API, also exercise the real code against it, read-only: copy `go.mod` and the package into a scratch dir under `/root/scratch` and add a throwaway `cmd/` there that calls it, credential in an env var — the repo tree stays clean, and what gets checked is the query the code sends, not a paste of it through another tool.
6. PR: title `feat: ...` in the repo's cadence, body = what changed / readings / verified (commands + SHA + real numbers) / left out, with each acceptance or done-line mapped to the test that proves it, `Closes #<n>`, reviewers `thani-sh` + `thani-sh-momo`. Watch CI with `gh pr checks <n> --watch` and confirm the gate steps ran, not just the job.
7. Move the card when the PR is open: `gh project item-edit 2 --owner aivara-se --url <issue url> --field Status --value Started`. One run per look: no second card.
8. Finishing move after the merge: verify `state,mergedAt` and the merge commit at main's tip, read the gate run the merge triggered on main (the Format/Vet/Test steps, not just the job) and run the local gate on the pulled main; then item-edit the card to `--field Status --value Finished`. Read the board first — if the column already reads Finished, no write; the state stands only once the build is verified landed.

## Pitfalls

- `gh pr checks <n> --watch` can outlive the terminal tool's own timeout when a runner is slow (an apt step can take minutes). Poll `gh pr checks <n>` with short sleeps and read `gh run view <id> --json jobs` for the step that is running; a pending status alone is not a stuck gate.
- `gh project item-edit 2 --owner aivara-se --url <issue url> --field Status --value Started` works as written on gh 2.102 — no field or option IDs needed. Read the column back with `gh project item-list 2 --owner aivara-se --format json`; the item's `content` carries no assignees, but the issue API does (`gh api repos/<owner>/<repo>/issues/<n> --jq .assignees`).
- A card that freezes a package's surface (e.g. `audit.Line` under #69) leaves no room for a new field: carry new identity in the pass's *own words* — the decision text and the dead-letter miss reason — and record that reading in a named PR-body section rather than adding an export.
- A change that makes a card's identity (the repository and the number) the thing the pass carries is not finished when the keys, the records and the writes carry it: the run's own input — the wake reason, `ADR 009`'s surface — is where two cards of one number still collapse into identical words, and the reviewer reads the argv. Pin it with a test that asserts the real invocation line names its own card (`--profile mama chat -q "card aivara-se/dispatcher#9 …"`), and check the record that already rules on the reason rather than opening a card for it.
- Prove a new test bites before claiming it: put the pre-fix line back (e.g. key the look's claimed set by number alone), run the one test, watch it FAIL, then `git checkout -- <path>` — restore from git, never from a hand-kept copy, and never leave the mutant in the tree. The reverse reading judges a peer's coverage finding: delete the guard it names, and a suite that stays green proves nothing pins it, so the fix is a test and only a test.
- AGENTS.md edits are sometimes consent-gated in this sandbox, and that prompt can time out while the operator is away. Attempt the write once: a `patch` carrying the entire old and new body goes through on these checkouts (`aivara-se/.agents`, a repo's own root file). Only when the approval actually times out leave the file untouched and name its stale lines in the PR body — do not retry, and do not conclude the file is unwritable before trying. A timed-out gate is cleared by the operator, not by you: state the exact lines you need, and when he says to try again, re-issue the same write — it lands, and no other route is permitted.
- `write_file` refuses an existing tracked path ("last read with offset/limit pagination") even after a full `read_file`, because it compares against the committed blob, not the worktree. Rewriting a whole document is `patch` with the complete old body as `old_string` and the complete new body as `new_string`; a long old_string is expected, and the returned diff is the proof it landed.
- The `write_file` refusal "modified by sibling subagent" is evidence, not noise: another session with the same identity is working in the same bind-mounted sandbox. Stop editing immediately — do not patch over foreign edits, do not keep iterating the same file. A peer on the same identity can also sit in another container that shares the bind mount, so its processes never appear in your `/proc` and the hermes child you saw is only your own: do not trust an empty process list to mean "no peer". Detect the peer by the worktree instead — the card's branch already exists with an unpushed commit, and the shared worktree's file mtimes and new `/root/scratch` artifacts (PR-body drafts, `dpid`/`exit.txt` hand-boot files, audit logs) advance while you read. Watch mtimes for a minute before concluding a run is dead; a look's "no run in flight" snapshot can predate a peer that is mid-delivery. Then check `gh pr list --repo aivara-se/<repo>` and `git branch -a`: if a peer already has an open PR or a branch for the card, your run is a duplicate; clean up your own unpushed leftovers (delete untracked files, `git branch -D` your local-only branch), verify the peer's PR against the card's done-lines, and report the twin-run to the operator factually. Never open a competing PR for a card another run holds.
- Read the item's `state` right before you write anything: a twin run with your identity can answer the same changes-requested review, get it approved and merge while you work. If it is MERGED and the fixes are in the tree, verify and stop — drop your unpushed commit, open no competing PR; `git diff --stat <reviewed head> <merge commit>` empty proves the merged tree is the reviewed one.
- A tinyjs desktop app is checked by booting the build: copy `dist/*` (`pereda` alone fails without its sibling `launcher`), `Xvfb :99` then `DISPLAY=:99 ./pereda`, type with `xdotool windowfocus <id>` + `xdotool type` (`windowactivate` fails with no WM), click by screen coordinate read off `import -window root`, and read the result with `bun:sqlite` over a copy of the app's real data file plus its `-wal` (the per-launch `/tmp` dirs are not the data folder).
- A comment or doc that conflicts with the change is deleted, not rewritten; the map in AGENTS.md is fixed in the same PR it stops matching — AGENTS.md included, subject to the consent note below.
- Never move a card another agent holds; the board is the source of truth and the service's future self writes only the assignee.
A sibling session can drop a foreign untracked file into the shared clone mid-run (`wire_test.go` appeared eleven minutes into one run), which breaks the whole package build. Never `git add .` — commit named paths only — and edit, gate, and commit in your own worktree under `/root/scratch` (`git worktree add`), leaving foreign files untouched. Uncommitted drafts from dead runs sit on top of main from time to time: `git stash push -m` them with a dated message instead of deleting.
- **A peer in the shared clone can undo your staged change between two commands.** The worktree is one directory, so another session's `git stash`/`git reset` leaves `git status` showing four staged files in one call and `git commit` answering `nothing to commit, working tree clean` in the next — and that peer may commit to your branch under your own name while you read. Stop editing that clone: clone it once into a private directory (`git clone ~/github/<org>/<repo> ~/github/<org>/<repo>-<agent>`, then `git remote set-url origin <the real URL>`), symlink the original `node_modules` in so the gate runs without a reinstall, and commit and push from there. Before claiming a branch is yours, `git log --oneline origin/<branch>` for commits you did not write; if foreign commits are on it, never rewrite them — carry on top and name them to the operator.
- A peer may already have pushed the branch and opened the PR minutes after the operator's snapshot: re-verify everything its body claims (gate, `-race` soak, doc citations) rather than inheriting them, fold any fix into one commit of your own, and never force-push a public branch — push on top. Taking over as assignee means owning the PR body: name what you found, your SHA, and what you verified.
- A `gh project item-list` item's content carries no assignees: read a card's live assignee off the repository's own board client (a `ReadAll(ctx)` adapter over `board.Client` in a scratch `cmd/`) — that one run is also the card's read-only live exercise: the pass runs over the real board with printing writer and runner, nothing is written anywhere, and the decisions double as proof the interface shape fits.
- `dispatcher` and `.website` both allow **rebase merges only** (`allow_squash_merge` and `allow_merge_commit` are false), so check `gh api .../pulls/<n> --jq '{mergeable,rebaseable}'` before claiming a PR can land: both must read true, and every branch commit must replay onto main on its own. A new test placed in lines `main` — or a parallel approved PR — also edited (the same function, the same fixture call) leaves `rebaseable: false` even though the final tree would three-way-merge clean; a later commit that moves the test does not repair it, because the rebase replays the offending commit alone. Put new tests at a location the other changes leave alone, and re-check `rebaseable` after every push.
- When main moves under your branch (a peer's PR merged first), *all* your branch's SHAs change — unavoidable with a rebase-only merge, and the same thing GitHub's "Update branch" does. Rebuild rather than hand-resolve 20+ hunks per commit: `git switch -c tmp <your head>`, `git merge --no-commit --no-ff origin/main`, resolve the one conflicting file (mechanical fixture conflicts resolve as the union — main's `boot(t, …)` with your own `card(…)` fixtures), prove `gofmt`/`vet`/`test` green, capture it with `git write-tree`, then reset your branch to `origin/main`, `git checkout <tree> -- .` and land it as one commit; assert `git rev-parse HEAD^{tree}` still equals the tree you verified. Squash the reviewed round-commits into that one commit — a rebase-merge repo lands each commit, so intermediate ones that no longer compile are exactly the WIP commits the house rules forbid. Force-push with `--force-with-lease=<ref>:<the head you are replacing>`; never rewrite a peer's branch or main.
- Two traps when you exercise a process tree from a test or a shell. (1) `/proc/<pid>/environ` can read empty for a moment after a child execs, even though Go's `cmd.Start` waits for the exec — a recognition check that reads it immediately is flaky under load; poll for the value (bounded) instead of asserting once. A child that forks without exec'ing keeps its parent's `cmdline` and group, so matching on the command line alone counts forks twice; require the group leader (`pgrp == pid`, from `/proc/<pid>/stat`) as well. (2) `pgrep`/`pkill -f <pattern>` match your own shell's command line when the pattern appears in it — the shell kills itself (exit 143). Run a pidfile or bracket the first character (`[d]ispatcher`) so the pattern does not match the caller. Kill a background server by the pid it wrote, never by a `-f` pattern.
- A job started through the terminal tool's background mode runs under a wrapper (`nohup bash -lc …`) that can `cd` to `$HOME` before your command, and the pid the tool reports is the wrapper's. An artifact written to a relative path — a file named for the process's working directory — then lands beside `$HOME`, not where you looked. Run a bounded job in the foreground instead (`cd <dir> && timeout -s TERM <n> <binary>`, read the exit code and the files), or find the real child with `pgrep -x <binary>` and read the artifact by absolute path.
- Inserting a declaration above another with `patch` means the anchor line must appear again at the end of `new_string`. Replacing the whole `func X(` line with the new block deletes that signature, and the file then fails to parse one declaration later — run `gofmt -l .` (or the compiler) on the single package right after a structural patch rather than after the next three edits.
- When the directory a terminal session sits in is deleted, every later call fails with exit 126 before the command runs. Re-issue with an explicit `workdir`; the session's cwd is not recoverable on its own.
