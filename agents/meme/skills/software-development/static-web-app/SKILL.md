# Static web app

The app is committed files the browser loads directly — no bundler, no build. This is how to run it, check it in a real browser, keep it working offline, and let the user see it.

## When to Use

Open this when the work is a small browser app with no build step:

- writing or changing it (HTML/CSS/JS served as committed files);
- serving it locally and checking it in a real Chrome;
- making it work offline (service worker, PWA manifest);
- putting it in front of the user to open and check himself.

## Serve it

- Write a tiny static server as a Bun script under `scripts/`, run with `bun run scripts/<name>.ts` (Bun for scripts — never Python or a shell script). `templates/static-server.ts` is a ready copy.
- Map the root **before** choosing the content type: `if (path === "/") path = "/index.html"`, then read the type from that final path. Getting it backwards serves `/` as `application/octet-stream`, and the browser downloads the page instead of rendering it — while every DOM-level check still passes, because they fetch the document, not the tab.
- Check status **and** content type for `/` and every asset: `curl -sS -o /dev/null -w '%{http_code} %{content_type}\n' <url>`. `text/html` for `/`, `text/javascript` for modules, `application/json` for a seeded data file, the media type for audio and images.

## Verify in a real browser

- Have a browser: `bun add -g playwright && playwright install chromium`. Before installing, check whether the machine already has them — a global install can exit 0 having downloaded nothing because the browsers sit under a different `PLAYWRIGHT_BROWSERS_PATH`. Launch with `--no-sandbox` (as root); a headed window needs `Xvfb :99 -screen 0 1280x800x24` and `DISPLAY=:99`. How to find them, and how to run a harness out of a scratch directory: `references/browser-checks.md`.
- Send real key events (`page.keyboard.down/up/press`), not synthetic dispatch, so the app's own handlers and the browser's repeat flag are exercised. One exception: the driver pins `key` to the value in its key table — `press("A")` arrives as `key: "a"` — so it cannot reproduce a `key` that differs between keydown and keyup. For that, dispatch a `KeyboardEvent` per event with the two `key` values and the same `code`.
- Measure timings **in the page**, never across the driver boundary — the recipe and the numbers are in `references/browser-checks.md`.
- Assert **geometry** with `getBoundingClientRect()`; number-and-position claims never come from a picture. Screenshots are for the user.
- **Sound is not in the DOM**: count `HTMLMediaElement.prototype.play` calls to turn a spoken-behaviour claim into a real check — `references/browser-checks.md`.
- For look and feel — spacing, density, whether it matches a concept — a screenshot *can* be read back. Load it into an image-capable model (`vision_analyze`) and ask a narrow question. The model is a rough design eye, not a ruler: it will keep saying "cramped" and its pixel estimates are noisy, so measure the concept's proportions (cap height, baseline spacing) and match those numbers instead of chasing it.
- It is a poor ruler but a good **defect sensor**. When it describes something structurally odd — an emoji with no word beside it, a chip it calls cut off, letters at a different size from their neighbours — treat that as a lead and go measure, because it is reporting a shape rather than a number. It flagged a chip split across a line break that every geometry check had passed, and the answer was one `getClientRects()` call.
- **Vision can be gone for a whole session.** `vision_analyze` can refuse every image with `ModelProtocolUnsupported` — the backing model has no eyes — so never plan a design review around it. The DOM carries the review alone: `getBoundingClientRect()` plus computed `fontSize`/`fontWeight`/`letterSpacing`/`color` for every key element gives fold positions, the type scale as rendered, the spacing rhythm and the colour tiers — a full measured critique with no picture, and the screenshots still ship to the user as evidence.
- Collect `console` errors and `pageerror` as a check of their own, and reload with the network off.
- Test the **returning visitor**, not just a fresh tab — a fresh profile always passes. `references/browser-checks.md`.

## Offline and the service worker

Precache the shell and bump the cache name in the same commit as any shell file; the trap is the **update path**, where a returning device keeps the old copy. Rules in `references/service-worker.md`.

## A store on the device

IndexedDB is what a page gets when it must keep more than a key: records, and pictures inside them.

- **Seed from files that ship, then read only the store.** Keep the built-in data as JSON (one file per record, plus an index naming them in order), read it into the store on a first run, and read the store from then on. From that point the store is the copy the app draws from, the user's edits included.
- **Precache the seed files with the shell.** They are fetched on a first run, so a first run with the network off has no data at all unless they are in the cache. Every file the app fetches to boot belongs in the shell list.
- **Carry a seed version.** Store a version beside the data and re-seed when it moves; that is how a shipped record reaches a device that already has a store — and it discards the user's edits, so say that plainly rather than let a user find out.
- **Draw the state that arrives late.** The first paint happens before an async read lands. Repaint when the data arrives instead of leaving the screen blank until the next input.
- **Write back only the record that changed.** Make the update helpers pure and return the *same object* for every record they did not touch; the caller then finds the one changed record by identity and writes only that one. Assert the identity in a unit test — the persistence layer depends on it and nothing else fails loudly when it stops holding.
- **A picture is a data URL, capped on the way in.** Scale the long edge to roughly 512px and keep the data URL on the record's own entry: no object URLs to revoke, and a screen rebuilt on every keystroke never carries megabytes.
- **Giving the user an editor means giving them undo.** An add-only editor for something a user curates is not coherent: a wrong entry is stuck, and the only escape is the nuclear reset. Pair the add with a remove, and pair a destructive reset with a confirmation that is two taps rather than a dialog.

## Share it

The user wants to open the running app himself. A quick tunnel exposes localhost: `cloudflared tunnel --url http://localhost:<port>` prints an `https://…trycloudflare.com` URL (install with `curl -fsSL -o /usr/local/bin/cloudflared https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64 && chmod +x /usr/local/bin/cloudflared`). Run it as a tracked background process, then curl the public URL for `/` and each asset to prove it end to end. The URL is ephemeral — it lives only while the tunnel process does.

- **Close it when the task ends, and prove the close.** The URL stays in the chat after the work is done, so an open tunnel is a live hole rather than a forgotten process: kill the tunnel and the static server, then probe both — the local port refuses and the public URL answers **530** (Cloudflare's no-such-tunnel error).
- **Kill by PID, never by a pattern your own command line contains.** `pkill -f "bun run serve.ts"` matches the shell running it, because the command text is in that shell's own command line, so it terminates your terminal (exit 143) before the intended process dies; a pattern loose enough to catch it (`serve.ts`) also catches another task's server in the same sandbox. Take the PIDs from `pgrep -f "[s]erve.ts"` — the brackets keep the pattern out of your own command line — or use the process tool's kill on the tracked session, and `kill` them one at a time.
- **The process tool's own report is not proof of a shutdown.** A tracked session can read as exited (`backend_lost`) while the port still answers; probe the port and the public URL instead of trusting the exit.

## Rules this user holds

- **Input is append-only: never edit what the user typed, however nonsensical.** If a spec rule only works by removing or rewriting entered text, drop that rule and say so. The same principle governs a side effect: when fast typing must not be read aloud, write every character at once and **debounce the sound** (speak a letter only when no other arrives inside the window) rather than delaying or dropping the character. Silence the accessory, never the text.
- A case change he asks for is a **display** change: `text-transform: capitalize` on the chip leaves `textContent` exactly as typed, so the append-only rule still holds and a check can assert both halves at once. Never let a display rule rewrite, retitle or "correct" the text. Every per-item decoration takes that shape: draw a chip's emoji with `content: attr(data-emoji)` and its colour from a `[data-color]` rule fed by the item's own data, so the DOM holds nothing but the typed text and a `textContent` assertion keeps passing while the pill gains an emoji. `attr()` reaches text only; a picture needs a real element, and an `<img>` prepended into the chip carries no text either, so `textContent` still reads exactly the typed characters. Keep the shape in the stylesheet and never in the data — a picture the parent uploaded is stored as uploaded and drawn as a circle by CSS, so changing the shape later costs one stylesheet value instead of a re-upload by every user.
- **Show each fact once in a row.** A row that repeats a value — a preview chip *and* an editor field for the same emoji — is read as a duplication bug by anyone looking at the render, and the browser's grey placeholder sitting among ink is then read as a disabled control. Let the editable field be the display; keep a picture's thumbnail as the only extra thing, because the picture is what the field cannot show.
- **Colour is data, not taste, and never the only signal.** The choice belongs in the data with a named fallback chain — the item's own value, else the colour of what it depicts, else its group's, else the default ink — and the chain wants a **live** last step (one group with no colour at all) rather than an empty branch, so the default is exercised by the app rather than only by reasoning. Every value is measured against the surface before it ships: a check reads the tokens out of the CSS, computes the contrast in the page, and fails under 4.5:1. The mark is carried by the outline and the meaning by the emoji, so a colour that renders badly on some device costs nothing that matters.
- **Curate the colour of a depicted thing; do not sample the picture.** Drawing each item in its picture's colour is a reasonable ask, and sampling the glyph's pixels to get it does not work: a pictograph is multi-coloured and skin tones and warm neutrals win the count, so a robot and an open book both came out "orange". Decide the mapping from what the thing **is** — an apple red, a frog green — and leave out the items whose picture says nothing about them, letting those fall down the chain. Then say in the notes that the map was curated by meaning, or a reviewer reads it as an unverified guess.
- **A bright pictograph colour rarely clears 4.5:1 on white, so it ships darker than the thing it depicts.** A banana's yellow has to become a dark gold, and anyone reading the render calls it tan. On a near-white surface legibility wins — resolve it that way and say which way you resolved it, so the compromise reads as a decision rather than a miss.
- The repo's spec docs are authoritative. When a change contradicts one, surface the conflict and get the decision before building — do not quietly override it. Once he decides to overrule a document, rewrite **that document** in the same change; a spec that still describes the old design is a bug of its own.
- **A documentation link he sends is a request, not a specification of the mechanism.** Check that the API it names exists for a page served from a URL — a good part of the `chrome.*` surface is reachable only inside a browser extension, and a static app is not one. When it does not apply, build the page's own equivalent and say which API you used and why it differs; do not silently build something else, and do not build against the named API anyway.
- **The text screen is a normal page: left-aligned, wrapping at the right edge, inside even padding, with a caret that moves with the text.** Where the block is anchored vertically is his call and it has already moved once — it now sits on the **bottom** (newest line on the bottom padding, older lines moving up as the text grows) — so keep the anchor as one named dial rather than baking an origin into the layout. The one thing he has rejected outright is a caret pinned to a fixed point.
- Take the look from the concept image, not from taste; if there is none, ask for it rather than guessing colours. The concept is also the ruler for **spacing and size** — read its proportions off the image (cap height and baseline spacing as fractions of the frame) and match those numbers.
- He tunes the look over several passes, one attribute at a time ("more relaxed", "more space around the pills"). Keep the look in a handful of named CSS dials — text size, `line-height`, `letter-spacing`/`word-spacing`, the outline's `padding`, the screen's `padding` — and move only the dial the request names. Say which dial you moved, so the next pass is one number rather than a redesign.
- Back every claim with real output: quote the command and the tree it ran on.

## Pitfalls

- **If a build step arrives, this skill stops applying.** The moment the repository gets a bundler, `scripts/serve.ts` and a hand-written precache list are replaced by the framework's own dev server, its two-pass type check and a build-generated shell list — and any document claiming "nothing builds between the committed files and the published ones" is now false and has to be fixed in the same change.
- **A toolchain that serves the build may cache the directory listing.** `vite preview` reads `build/` once: rebuild underneath it and the new hashed files 404 while the old ones still answer, which reads as a blank page and `Failed to fetch dynamically imported module`. Restart the server after every build. The same server refuses a foreign `Host` header with 403, so a tunnel needs your own static server over the built directory.

- **A class rule defeats `[hidden]`.** An author `display: flex` on a panel overrides the browser's `[hidden] { display: none }`, so a panel set `hidden` stays on screen. Add `[hidden] { display: none !important }`.
- **A full-screen overlay needs a background *and* a stacking position.** Without a background it shows the layer beneath it; left in normal flow it is painted *under* a sibling that is `position: fixed`, so a panel meant to cover an always-visible full-viewport play layer vanishes behind it. Give the overlay `position: fixed; inset: 0; z-index: 1; background: var(--surface)`.
- **Do not probe a custom `[hidden]` rule with a fresh `<div hidden>`.** The user-agent default already hides it, so the probe passes with or without your rule. Probe the served CSS (`fetch("styles.css")`) or a real element your rule governs.
- **A text screen that outgrows the viewport must scroll itself.** `overflow: hidden` still scrolls programmatically: after each character set `screen.scrollTop = screen.scrollHeight`, which keeps the newest line in view without a scrollbar for a child to grab. (The top padding scrolls away with the content — that is normal.)
- **A caret drawn as an inline element changes where the line wraps.** Cancel its advance with a negative margin (`margin-left: 0.05em; margin-right: calc(-2px - 0.05em)`) so it never pushes a character to the next line. Leave it a small gap from an adjacent word outline too — flush against it, the caret reads as part of the outline and looks like there is no cursor at all.
- **"Taller" means both ways, and `vertical-align` decides the one way a bar does not grow.** `vertical-align: text-bottom` keeps an inline-block bar's foot on the text's bottom edge, so raising its `height` extends it upward only — he calls that one-sided and rejects it. `vertical-align: middle` centres it on the x-height; `vertical-align: -0.5em` with `height: 1.7em` centres it on a chip's middle instead, so it overhangs the chip above and below by a matching amount. Size both `height` and `width` in `em` so they scale with the text, and keep the negative `margin-right` equal to `width + gap`.
- **Never switch off an animation that is the point of the element.** An `@media (prefers-reduced-motion: reduce)` off switch is right for decoration and wrong for a caret he asked to pulse: his device reports reduce-motion, so the pulse never ran and he reported it back as "it does not animate right now". Ship the pulse running whatever the device reports, and say so in the design doc so the next pass does not re-add the switch.
- **A pulse eased between two endpoints is a triangle, not a wave.** `ease-in-out` from full to a third holds flat at each extreme and turns a corner there, which is what "like a sine wave" is asking you to stop doing. Sample the law into the keyframes — `opacity: (1 + cos(2*pi*t)) / 2` every 5%, trough exactly 0 — and set `animation-timing-function: linear`, so the shape is the wave's and only the keyframes carry it.
- **An inline element's padding and border make no space *after* it.** They sit inside the border box, so whatever follows — the next character, another outline, the caret — starts flush against an outlined word. Only a `margin-right` on the outline puts a gap after it; give every outlined chip one, and give the caret its own small gap besides.
- **A line break inside an inline chip splits its outline into separate pieces.** An inline box fragments across lines, so the border is drawn around each piece and `getClientRects()` returns one rect per piece — an emoji ending one line with its word starting the next, each in its own broken outline. `overflow-wrap: normal` does **not** stop it, because the break falls between the `::before` box and the text rather than inside a word; only `white-space: nowrap` on the chip holds it together. Assert one client rect per chip, or nothing in the geometry checks notices.
- **A font carries its own empty space above and below the glyphs, so equal CSS padding does not look equal.** The ascent and descent the font reserves dwarf the side bearings, so a chip padded the same on all four sides reads top-heavy. The vertical padding is a dial he tunes, and equality was only the first stop: he then asked for the top tighter again, so the word sits high in the chip — `padding: 0.08em 0.32em 0.15em`, measured at 27px above the tallest letter against 40px below and 35px to each side. Move only the side he names, and say the CSS is deliberately uneven, or he checks the box numbers against "the same on all sides" and calls it unmet. Measure the ink from the pixels, never from the box or from a canvas metric: recipe in `references/browser-checks.md`.
- **Track keys by `event.code`, never by `event.key`.** `key` is the character the modifier state produces, not the key: hold Shift and release it before the letter, and the same key reports `"A"` on the way down and `"a"` on the way up. A down/up map keyed by the character never clears that entry, and when the entry means "a key is down" every later press is judged against it and the keyboard goes silent for good — reported as "it stops accepting input after I type a capital". Keep the character from the press for what gets written, identify the key by its code, and release by code alone so no press can be left behind.
- **A border's width snaps to a whole pixel; a background does not.** Ask for a 4.9px border and the browser draws 4px, so a bar whose width carries the same value renders 0.9px fatter and the two never match. Pin a thickness that must agree between a border and a bar as a whole-pixel token (`--stroke: 8px`), not an `em` value — and revisit the token when the text size moves, because a length is not a ratio.
- **Insert derived text on the settle signal, never on a pattern match alone.** A completed word wants a space after it so the next letter starts a new word; matching a listed word the moment it appears cuts a longer word in two: the four letters the child typed for "cats" are separated into the listed word, the inserted space, then the leftover letter. Fire the insert from the same idle timer that reads the marks, and only when a mark ends at the end of the text — a word still being typed is then left whole. Document the one character the app adds against the append-only rule.
- **In a container that mixes text and elements, do not range over `firstChild`.** A screen rebuilt per write starts with an empty text node whenever the text opens with a marked span, so `range.selectNodeContents(el.firstChild)` yields no rects and anything read off it throws. Range from the container's start to just before the element you know is last — `range.setStart(el, 0); range.setEndBefore(el.querySelector(".caret"))`.
- **Shading line boxes the browser created.** When the browser does the wrapping there are no per-line elements to style; `mask-image` is the way. Find the caret's line with a `Range` over the text — `range.getClientRects()` returns one rect per line box, the last is the current line — then set `mask-image: linear-gradient(to bottom, transparent <top - 2.5 * lineHeight>px, black <top>px)` on the screen, recomputed on every write so it follows the caret. A mask on a scroll container is fixed to its box, so it stays anchored to the screen while the text scrolls under it. It fades a line's top as well as the lines above; a stepped look needs hand-measured wrapping instead — say which you are giving him.
