# aivara-se workflow

A change here has one shape: find the document that owns the fact, edit it, sweep the copies, and land it by pull request.

## Where things live

- Repositories clone to `~/github/<owner>/<repo>`; the organisation's code is `aivara-se/<repo>`.
- **A new repository starts with its product document.** `references/new-project.md` is the bootstrap: create the repository, align settings, check the ruleset, land `PRODUCT.md` alone, then `SYSTEMS.md`, the ADRs and the entry file.
- **`aivara-se/.agents` is the fleet's shared configuration.** `agents/<bot>.md` is an agent's whole identity and the source of truth for what it is; `skills/` is what every agent reads. The donor entry file is the `aivara-se/.template` repository, not a path in `.agents`. The live skill set is the directories on disk (`find skills -name SKILL.md`).
- **A repository on the convention carries no copy of the skills** — no `.agents/skills/`, no `## Agent Skills` section in `AGENTS.md`. Every agent reads `~/github/aivara-se/.agents/skills` through `skills.external_dirs`. Enumerate with `gh repo list aivara-se`.
- **The entry file says what the service is, once, and carries no provenance.** Drop the template's overview paragraph when the repository map says it, and its "agent convention, version N, adopted from …" line: the pull request names the template.
- **The release standard is a process; each repository carries its own workflow.** `aivara-se/.github/docs/RELEASES.md` states the steps: read the version file, stop when the version is tagged and released, build, tag after the builds, release, then the registry when applicable. The YAML is inlined in each `.github/workflows/publish.yml`. Cutting the bump itself — which document lines move and which must not, the changelog and Roadmap edits, the gate, and the release pull request — is `references/release-bump.md`.
- **The baseline is `aivara-se/.github/docs/SETTINGS.md`, checked by `scripts/verify-settings.ts`.** Merge method, the required `validate` check, the review count and the empty bypass list are the ruleset's, not a preference. `GH_TOKEN=$(gh auth token) bun run scripts/verify-settings.ts --repo <name> --json` reports what a repository carries; a `403` on an Actions or security setting is a missing administration read, not a finding.
- **The document standard is `aivara-se/.github/docs/DOCUMENTS.md`, checked by `scripts/validate-docs.ts`.** `PRODUCT.md` has six headings inside 600 words; `SYSTEMS.md` three inside 300; `README.md` and `DESIGN.md` have a shape and no budget. The pair is read from the repository root or `docs/`. The reusable `.github/workflows/validate-docs.yml` runs it with `--require`; a repository adds it as its own `docs` job, in the pull request that brings its documents into line, so the required `validate` check keeps its name.
- **A licence is per repository; the organisation carries no default.** `references/licensing.md` is the pass: detect with `gh repo view <repo> --json licenseInfo`, fix the licence and copyright line, then land `LICENSE`, the README pointer, the manifest field and an ADR in one documents-only pull request — the record naming what earlier tags do not carry.
- **A page on `aivara.se` is six files and one test.** `references/website-page.md` is the recipe — the route helper, the roster path, the header icon, the dictionary strings, the data file, the component, and the assertion that keeps them in step; `scripts/shoot-page.cjs` renders a built page in Chromium at the two widths the design fixes.
- **Treat board scope and repository scope separately.** To act on a column, enumerate project items and filter by the exact `Status`, resolving each issue URL; `gh issue list` misses issues off the board or in another column. For a destructive request, confirm whether the user means delete the issue, close it, or remove only the card. Writing one — issue, project item, column, claim — is `references/board-project.md`, with project #2's field and option ids and the one-turn card-then-build rule.
- **The wake procedure lives in the organisation's `dispatch` skill.** `aivara-se/.agents/skills/dispatch` owns what an assignment, a review request, a `changes requested` review, a failed check and a mention each mean, and how a pull request is opened and answered. This skill carries the other half; do not restate its rules here.
- Mail: `himalaya` reads the shared account as `-a aivara`.

- **One repository is often cloned twice.** A second checkout can sit beside the canonical one. The shorter path reads as authoritative, yet it can be dozens of commits behind. Three tells: `git status -sb` prints `behind N`, a branch's upstream reads `[gone]`, or `git remote -v` answers one URL from two directories. Author from the copy whose `origin/main` is the head you branch from.

## Doing the change, in order

1. **Fetch before believing a checkout.** Read the fetched ref, not the working tree. Run `git fetch origin`, then `git log --oneline origin/main`, `git branch -r` and `gh pr list --repo aivara-se/<repo> --state all`. Do this before you cut a branch, edit or quote a file. An open pull request on the same decision is the change to review, not a second one. A remote branch with no pull request is work in flight. `git fetch` moves refs, not files. Read `git show origin/main:<path>`, or fast-forward with `git merge --ff-only origin/main`. A glob in that path is not expanded, so take each path from `git ls-tree -r --name-only origin/main`. The tells are `git branch -vv` printing "behind N" and a version sentence contradicting `git log --oneline origin/main`. For a gate run, clone the remote URL: a clone of a stale clone passes the gate on a tree that is not `main`.

2. **Name the owner of the fact.** Read `aivara-se/.agents/agents/<bot>.md` before writing about a role, and a service's `docs/PRODUCT.md` and `docs/SYSTEMS.md` before writing about it. Never write a role from memory or a draft.

3. **Sweep the copies on the fetched refs, hidden repositories included, and sweep for the rule as well as the value.** `search_files` skips dot-directories, so a pass over `~/github/aivara-se` misses `aivara-se/.agents` and `aivara-se/.website`. Run `git grep -niE '<old wording>' origin/main` in each clone, or point `search_files` at the hidden path. Roster example: `agents/<bot>.md` owns the title, `.website/src/lib/i18n/en.ts` carries the role line each card prints, and `.website/PRODUCT.md` states the rule that line must satisfy. A rename that changes the value's shape leaves the product document asserting a rule the copy breaks, which no search for the old wording reaches.

4. **Classify blockers before asking.** Separate operator-owned files or decisions from edits you can make. Do every independent fix; ask only for the smallest unavailable input, naming the path or decision that waits.

5. **Synchronise the work item before coding.** Put a missing acceptance rule into the issue/spec in the same workflow, read it back, check it is precise. Cards are executable specifications, and an ambiguous rule recreates the stale design. To remove a design card, partition its rules into the implementation cards that own them, edit those with only their interfaces and done checks, read every edit back, close the source issue, then remove only its project item. Leave repository documents untouched when the cards are the temporary specification.

6. **Make the smallest edit that removes the stale claim.** Match the document's register and the `writing` skill. Where the change turns on a new distinction, state both halves, and keep a negative rule negative.

7. **Verify before opening the PR.** In a bun repository run `bun install --frozen-lockfile` first: `bun x tsc` alone fails `TS2688: Cannot find type definition file for 'bun'`. `/tmp` is noexec here, so a Go gate is `mkdir -p $HOME/tmp && TMPDIR=$HOME/tmp go test ./...`, or every package fails `fork/exec … permission denied`. Then `git diff --check` and a link check. An acceptance sweep names the path, not just the filename: `rg 'docs\.yml'` also matches `validate-docs.yml`, so the check fails on the fix it was written to prove. Report skipped checks accurately; never claim green on one. Run `actionlint <path>` on every workflow the change touches: GitHub expressions have no `replace()`, so a name assembled with it is rejected at load while the YAML reads valid. A green run is not proof your branch ran — a job whose `if:` is false reports success without executing — so read the log for its line (`gh run view <id> --log | grep -i 'nothing to publish'`) and the artefact it claims (`gh release view <tag> --json assets`). A checker that finds nothing is green too: a job printing `validate-docs: no documents here` has read no file, so make the caller demand its input (`--require`) and grep the log for the pass line, not the tick.

8. **Land it by pull request, never on `main`.** Run the branch, commit, push and `gh pr create` sequence yourself; hand delivery to Root or another agent only on explicit delegation. For a contribution to a peer's open pull request, push one focused commit to that head, comment the sha, and leave the review to the operator: a stacked pull request is the wrong shape. Branch `docs/<slug>` (or `feat/`, `fix/`) with a typed lowercase subject (`docs:` then an imperative phrase), and a body: what changed, why, what was verified, what is out of scope.
   - **Mid-restart, the base is the restart branch** (`gh pr create --base next`). `Baseline` guards `main` alone, so a restart-based pull request reports `mergeStateStatus: CLEAN` with no required review; read `gh pr view <n> --json baseRefName,mergeStateStatus,reviewDecision` before calling it blocked.
   - **Reviewers.** Operator (`thani-sh`), plus one peer (`thani-sh-meme`, `thani-sh-mimi`, `thani-sh-momo`) for implementation. A documents-only change is reviewed by the operator alone: peers review code, not design. `reviewRequests` reads `["thani-sh"]` and nobody else, and is read back to prove it. **A list the operator names replaces this default, whatever the artifact** — two peers on a documents-only draft is their call, not a misread: request exactly the logins named, and read them back.
   - **The reviewer the operator names classifies the artifact.** "Add only me as a reviewer" says documents-only, so new workflow YAML stays out.
   - **`gh pr create --reviewer` can fail after the pull request exists.** Re-apply with `gh pr edit <n> --add-reviewer <login>` and read `reviewRequests` back.
   - **Every push re-requests review.** A submitted review empties the list, so after every push run `gh pr edit <n> --add-reviewer <login>` for the whole list.
   - **A fix commit does not answer a reviewer.** Read `gh api repos/<owner>/<repo>/pulls/<n>/comments` for inline findings and `pulls/<n>/reviews` for the verdict — `gh pr view --comments` misses both — then comment each finding against its fix.
   - **A push falsifies the body.** Re-read it against `git diff origin/main` and rewrite it when a commit lands what it called out of scope or widens the files.
   - **Answer a finding by changing the record it named.** An older ADR is immutable, so a falsified clause takes a new ADR naming what it overrides.
   - **The merge is this agent's standing act.** An approved, clean pull request is MaMa's to land. The approval can never be her own: `Baseline` requires one approving review and GitHub refuses a self-approval, so her own pull request sits `BLOCKED` / `REVIEW_REQUIRED`. Report it as waiting; never force it.
   - **Grade a red check against the ruleset's required list** (`gh api repos/<owner>/<repo>/rulesets/<id>`). An unrequired check leaves `mergeStateStatus: UNSTABLE` — still mergeable — where `BLOCKED` means a required thing is missing. A code-scanning analysis with no source on the branch is the repository's setup, and the operator's to change.
   - **Merge with the method the repository allows.** Read `gh api repos/<owner>/<repo> --jq '{squash:.allow_squash_merge,rebase:.allow_rebase_merge,merge:.allow_merge_commit}'`; these repositories are rebase-only. A rebase merge lands every commit, so keep each one final.
   - **A behind head refuses the merge on a required check.** `gh pr merge` answers `Required status check "validate" is expected.` when the head predates the last run of that check; nothing is missing and the review still stands. Bring the branch current (`gh pr update-branch <n> --rebase`), wait for `gh pr checks <n>` to pass on the new head, then merge. The check is bound to the head sha, so a rebase-only repository needs the update anyway.
   - **Prove a long-lived restart branch reverts nothing** with `git merge-base --is-ancestor origin/main origin/next`: false means `main` gained commits after the fork and the merge drops them. Read `delete_branch_on_merge` in the same call; with it on, a merge deletes a long-lived `next`. Raise it first, or recreate the branch afterwards.
   - **Report the link whenever a pull request is opened**, in the same turn, without being asked.

9. **Report the ripple.** Name the other repositories and cards still carrying the old fact, and any decision left open — as follow-ups, not silent scope. Say so when the change came as a chat request rather than a card in `Backlog`: the board is the record. A merge that closes a card goes stale elsewhere: read the repository's open pull requests for that number first, land the text-only ones in the order their lines depend on, and correct a line of your own rather than leaving it for a reviewer.

## Handing implementation to a peer agent

For a prompt to a builder — MeMe, MiMi or another agent — start from `templates/handover-prompt.md`: the documents are the specification, the design is frozen, the work lands as one pull request, and the builder stops and asks on a blocker rather than deciding one. Name the gate, the acceptance checks, and the values only the operator knows as questions. The issue that carries a version — title, label, assignee, its five sections, and its records on `main` before the wake — is `references/version-issue.md`.

## Answering "what is this issue about"

A question about one item is a read pass answered in one message: what it claims, whether the claim holds, and whether it is still open work. Read the item whole first (`gh issue view <n> --repo aivara-se/<repo> --json number,title,state,body,labels,comments`), then check its claims against the tree.

1. **Read a cited artefact at the commit the item names, not at the working tree.** `git show <sha>:<path>` and `git log --all --oneline -- <path>`. A repository can be reset to an earlier document set, so a cited ADR is absent from `main`'s `docs/adrs` listing yet present in the named commit; calling the citation wrong from a directory listing of the head is the false finding.
2. **Check for the fix commit before repeating a finding.** `gh api "repos/aivara-se/<repo>/commits?path=<path>" --jq '.[] | "\(.sha[0:7]) \(.commit.message | split("\n")[0])"'` lists the edits to the file. A commit after the item's creation that answers each point means the item is resolved.
3. **Report state beside content.** When an open item is already fixed on `main`, name the commit and say that closing is the only act left; do not leave the operator to infer it from prose.

## A pass over the state: built, in flight, waiting

Answer a status request from the board and the code, never from the cards' prose: enumerate both sides, diff them, prove what you can. A count of published entries is the live page's, and a merged pull request counts only after its deploy completes.

A document-set pass asks about its consumers and the decisions after it. `references/convention-audit.md` is that loop, the repair pass after it (one pull request per repository, the donor first), and the design pass for changing the standard itself.

- **Enumerate the board and the open issues separately.** `gh project item-list <n> --owner <org> --limit 200 --format json`, parsed in code because the listing truncates in a terminal, gives each card's exact `Status` — read it as `item.get('status')`, because a card in no column has no `status` key and `item['status']` raises `KeyError`. `gh issue list --state open --repo aivara-se/<repo>` gives the repository's side; `gh search issues --owner aivara-se --state open` covers the organisation. An open issue with no card, and a card whose issue is closed, are findings. Before calling a card-less issue a gap, read its timeline (`gh api repos/aivara-se/<repo>/issues/<n>/timeline --paginate`) for `removed_from_project_v2`: a deliberate removal says the card is not the unit of work.
- **An empty issue list is not "nothing pending": decided-but-unbuilt work is in an issue the ADRs name.** The standard's system document has no heading for it, so the decision stays in its ADR and the work in an issue; read both, then prove the item unbuilt (`ls internal/`, `grep -rn '/metrics' .`).
- **Run the repository's own gate yourself, at remote's head.** Clone the remote URL and run `gofmt -l .`, `go vet ./...`, `go test ./...` on the SHA you report; a green CI run on it is the second opinion. A run that fails once and passes on repeat is a flake: name the test.
- **The board moves while you work.** Re-read it before the report and timestamp anything that changed mid-pass: the operator moves cards by hand. A `Status` you set to match their stated move is theirs to overwrite — report the column when read, never re-applying your edit. Grade each card against its column: a deploy or acceptance card in `Refined` is written into a builder who cannot do it.
- **An assignee is a claim, not a run: the service never moves a card.** The service writes one field, the assignee, and starts that agent's run; v1 has no board flow. The move from `Backlog` to `Refined` is the refiner's act inside that run, so "assigned to MaMa" is the service's last act on a `Backlog` card, never a stalled step. A card under an agent's login is one of three states the column cannot tell apart: held for the operator, assigned by a hand, or a claim whose run never went. Answer "why is this card not moving" from its prose and timeline (`assigned`, `unassigned`, `project_v2_item_status_changed`, each with `actor` and `created_at`). Where every write carries one login, the timeline shows service writes and hand-moves as one actor.
- **No inbound delivery, no look.** The service acts only when a delivery arrives, a run it started ends, or at boot; there is no clock and no polling. Until the organisation webhook is registered, a new card generates no delivery and can sit unassigned in `Backlog` for tens of minutes. Once the assignee is written the card counts as claimed and is never woken again, so a claim whose run never started is repaired only from memory.
- **Prove a run's absence from the session store, not from the assignee.** The service keeps no run table, so a run exists only as its session: `session_search(profile=<profile>)` lists it under `<owner>/<repo>#<n>` with `source: tool`, where a chat turn on the same profile is `telegram` and a cron job is `cron`. No such session, no issue comment and no branch means the assignment started nothing — check every agent profile before calling the issue untouched, and report the sessions that did touch the subject with their last-active time rather than calling them active.
- **Grade a `Finished` card against its own _Done means_, not its column.** Read the issue's timeline (`gh api repos/aivara-se/<repo>/issues/<n>/timeline --paginate`, filtered in code to `project_v2_item_status_changed`, `closed` and `commented`, each with its `actor`) and its comments: a card closed with nothing said, where it demanded evidence on the thread, is a claim, not a delivery. A deploy or acceptance card leaves artefacts the tree can prove; check those first. The organisation webhook is the operator's to confirm.
- **Grade a restart branch against the default, not in place: its deletions are owed decisions.** To check a branch that is not `main`, fetch every head (`git fetch origin '+refs/heads/*:refs/remotes/origin/*'`), then read `git log --oneline origin/main..origin/<branch>`: a plain `git fetch` leaves the working tree on `main`, so read `git show origin/<branch>:<path>`. A `nuke!` commit leaves the surviving documents as the whole specification, so grade each rule against them and the decisions deleted with the code. An acceptance criterion the new scope keeps whose ADR went in the nuke is **unrecorded, not settled**: list the deleted decisions the new flow needs rather than resurrecting old files that name the dropped mechanism. Name the surface the new docs leave interface-less as what to settle before a builder starts. When the operator says which decisions to ignore, treat them as abandoned and keep the ADR number they named; a fact they fix that no document carries goes into the product document, noting the format is unrecorded.
- **Prove a suspected drift with a probe, not an argument.** When record and tree disagree, write the throwaway test in a scratch clone of the remote — never the repository — after reading that branch's test helpers for their current signature, and report the output. After an aborted merge test: `git reset --hard <ref>` then `git clean -fd` (`git checkout -- .` refuses while paths are unmerged, and the clean takes the probe, so write it after the reset).
- **Prove a suite's sensitivity with a mutation, not a coverage number.** Break the code in a throwaway copy and read which tests go red. `cp -r` the clone once per mutation, change one thing, run that package, and keep the table of mutation → before → after.
- **A test that loops over its own constant travels with it.** `for i := 1; i <= MaxFailures` passes at six as at five, so a promised number needs a literal assertion and a boundary walked at the number. The same shape hides a changed TTL or size bound.
- **A registry needs a row count and a reachability row.** Once flows or handlers come from a table, every per-flow test passes with a row missing: assert the table's length and drive one signed delivery through each entry, because a handler never registered compiles and fails no unit test.
- **Order is a contract only where a test reads the whole line.** Per-delivery tests leave the sequence and field set of an audit record free, so one golden burst compared byte for byte against the marshalled records is the baseline.
- **The safety net lands before the change it protects, in its own pull request, and passes unchanged on the old tree.** Name an untested entry point (`cmd/` at zero) as its own gap instead of averaging it into the package figure.

### Answering "what is left before it runs live"

A pre-launch question is a readiness pass: the work between the tree and a first run, grouped by whose hands each step is in.

- **Read the launch card's steps and _Done means_, then grade the tree.** Walk the cutover card's sequence and mark each step done, waiting or unstarted.
- **Enumerate the artefacts the documents claim, and check the tree.** A services doc asserting "the config file is committed to this repository" while the tree carries only a test fixture is a gap, not a settled fact — read the claim, then `git ls-tree` for the file. A future promise — "provisional until the deployment lands" — marks work only the live run completes.
- **Name an open defect the card omits, and say whether it blocks or is accepted.** A `Backlog` card with no assignee and no `blocked_by` edge is the one a readiness list drops.
- **Author a missing artefact from the documents or the loader, and surface the judgement call.** A committed config's shape is the loader's schema and the services doc's list, not the fixture. A value the documents do not fix is the operator's: pick the reading that makes the documented behaviour true, say so in the body, and name the revert. Prove it loads with the project's own loader in a throwaway test, then delete it: `go test` says nothing about a JSON file nothing imports. A new root file also goes into the entry file's _Repository Structure_ map, but not obvious plumbing.
- **Separate the hands explicitly.** Steps needing systemd, Caddy or a shell on the host are the operator's and Root's. Say which are yours and offer to do them.
- **A host handoff is an artefact, and names two user-unit traps.** Hand over the unit file, the environment-file shape (secret values at mode `600`; the committed config carries only their names) and the proxy site, with host paths as placeholders for Root. `loginctl enable-linger <user>` or the unit dies with the operator's last session; and a user unit's `PATH` is minimal, so a service that spawns another binary needs its absolute path on a flag — the bare command resolves in your shell, not the unit, and the first wake fails.

## Deciding and recording an architecture change

`references/design-decisions.md` is the loop: ground in the documents and past attempts, answer with options first, take a default on every fork that does not change the artifact, record the pick as an ADR before the code, and sweep the documents it falsifies. It also carries the conflict pass over the edited documents, _Probing a behaviour a decision turns on_, _Containerising a service that drives the host_, _Planning ahead across versions_, _Sizing a decided-but-unbuilt change_, and _Evaluating an outside design_ — what to take from another system's documents and what to refuse. A candidate that would stop a run in flight dies there: a wake starts a new run, not a message to one.

**The deliverable is the record until the operator asks for code.** A chat request for "the next version" is a design pass: land the ADR and the documents it falsifies as a docs-only pull request, and name the implementation out of scope. Do not start code from the same request; if ambiguous, ask.

**An ADR stands alone.** It cites only earlier ADRs, never `PRODUCT.md` or any document that moves with the version; documents link to the record, never the reverse.

**A visual decision's values land in `DESIGN.md`.** The product document says what the person sees in words; the numbers — geometry, type, colour, the motion tokens — live in the design document. Create the file when the repository carries none, and name the entry file's missing map line in the body: `AGENTS.md` is the operator's.

**A follow-up "would X be simpler?" is answered with the mechanism test, not a rewrite.** Say what the proposed structure owes — a lifetime bound, a kill path, a boot reconcile, a queue that spends one run per item — what the deleted tree already priced, and what would change the recommendation. When the answer holds, add one precision clause to the ADR, put the rejected candidate in the body, then push, re-read the body, and re-request review, because a push empties the request list.

## Refining a card in `Backlog`

A card is refined when it is feasible, complete and unblocked. Feasibility is a read of the code and documents it builds on: a card whose premise names a surface that exists only on an unmerged pull request cannot start.

- **A card that cannot start stays in `Backlog`, with its blocker linked.** Moving it to `Refined` hands a builder a surface that is not on `main`. Link the prerequisite with the native `blocked_by` edge (the `github` skill's _Sub-issues and Projects v2_), as the org's cards do, and say it in the prose.
- **A removal card is refined against the code's readers, not its prose.** Grep for who _reads_ the surface, not who names it — a single opener and no consuming document makes a removal sound — then find what it was the only _writer_ of: the miss file was the only record of a refusal that appended no audit line, so the card had to say the refusal stays an audit line and the reason goes to stderr.
- **Keep the refiner's assignee on a refined-but-blocked `Backlog` card.** The claim stops the next look waking the refiner again; an unassigned `Backlog` card is woken after every restart. The merge that clears the blocker moves the card on.
- **A `Refined` card carries no assignee.** The rule wakes a `Refined` card only when nobody holds it, so the move from `Backlog` clears the refiner's login in the same act; leaving it strands the card. An assignee in `Refined` or `Started` also holds that agent's slot.

## Pitfalls

- **Reissue a design pull request from a clean branch.** A rebase merge lands every commit, so each fix reads as churn. Past the first round, close it (`gh pr close <n> --delete-branch --comment …`) and open one fresh commit from `main`; a seen branch cannot be force-pushed. **Never stack it on another unmerged design pull request** — both edit the same `## Scope` and open-issue lines. **A reissue at a named commit is written, not cherry-picked**: `git checkout <commit> -- <paths>`, then commit under your own identity, because a cherry-pick puts the operator's name on a pull request that is theirs to approve.
- **`AGENTS.md` is the operator's: name stale lines, edit only when asked.** The protection is a convention, not a guard. When told to update it, edit on the same branch, re-run the link check and the gate, and correct a body that said otherwise. The donor keeps no state: a _Current Project Focus_ belongs in `PRODUCT.md`, a _Repository Structure_ map in `SYSTEMS.md`, and a stale one is a finding with no owner to name.
- **A rename hides in the local clone.** GitHub redirects the old URL, so an existing clone keeps fetching through it and never shows the move. Enumerate with `gh repo list aivara-se` and resolve one with `gh repo view <owner>/<old> --json name`. A pre-rename clone and a fresh clone of the new name sit side by side as twins — `git remote -v` disagreeing with the directory name is the tell. The old name also lives in the Go module path, the binary and `cmd/`, the config filename, the env prefix (`<NAME>_*`), and other repositories' fixtures.
- **A `nuke!` reset leaves the front door in its parent commit.** `git show <reset-commit>^:<path>` answers the lost `AGENTS.md`, `README.md` and committed config. Read them before writing replacements, then rewrite a house rule bound to the abandoned mechanism.
- **A document a test loads is pinned to the code.** A README example run through the real loader (`TestReadmeExampleIsLoadable` with `DisallowUnknownFields`) fails the gate before the loader accepts a new field. Grep the test tree for the path before editing an example, and leave the runbook's example, env file and event list to the pull request that adds the code.
- **A replaced mechanism falsifies the entry file's house rules: the operator holds the pen.** Read `AGENTS.md` for prohibitions the decision broke — "never call the API", "hold no credential", "keep no durable state" — and name each in the body as the operator's turn.
- **A standard that outgrows its first implementation states the steps and rules; each repository carries the workflow.** Do not factor a build or release pipeline into a reusable workflow in `aivara-se/.github`: shared packaging makes one change land everywhere. **A convention checker is the exception.** It must run identical code in every repository, because two copies drift and the convention then differs by repository with nobody seeing it. Share that one, and change it only in a pull request that changes the standard it enforces. A repository adopts it in the pull request that brings its documents into line: wired into a required `validate` earlier, it turns every unrelated pull request red.
- **A README written ahead links only paths the tree carries.** A link to a missing file is a broken link a reviewer fails, and a gate command naming a workflow nothing runs is a red check waiting. Add the workflow with the first code.
- **A request contradicting a written convention changes the convention, not the rule.** When the task needs a rule broken — a skill that must name another, under "skills stand alone" — edit the rule in the same pull request and argue the wording in the body.
- **Edit a repository from `execute_code` with absolute paths.** The helper runs in the profile's home, so `patch('docs/PRODUCT.md', …)` resolves under `~/.hermes` and the whole batch fails. Prefix the absolute clone path, or use `terminal` or the standalone `patch` tool in the repository's cwd.
- **The clone is shared, so the working tree can change between calls.** `HEAD` belongs to whoever last ran `git`, and another session may switch branches while your edit sits uncommitted. Read `git branch --show-current` and `git log -1` before every edit batch and commit, and treat a "file changed" warning as that checkout. If `HEAD` is not your branch, copy the file out, check out your branch, re-apply, and never commit onto a detached `HEAD`. For documents-only work, `git clone https://github.com/aivara-se/<repo> $HOME/tmp/<repo>-docs` and work there: `/tmp` is noexec, so a repository whose gate runs an installed binary cannot be checked there; for a pull request head, `git worktree add -B <branch> <dir> origin/<branch>` under `$HOME`, then `git worktree remove <dir>`. **The wake races you once the service is live**: read `gh pr view <n> --json state,commits,reviews` before pushing. **A `changes requested` wake commits to the branch you are editing**: the head can carry commits you did not make, so read `git log --oneline -5` and `git diff <branch point> HEAD -- <path>` before the edit, and change a file with a targeted patch — a whole-file write silently reverts a peer's fix in every paragraph you did not re-read. **Commit each document edit as you make it**: a peer run stages the whole tree, so an uncommitted edit lands inside its commit under a message that names something else, and the body then quotes a sha whose commit does not describe it. **Remove the worktree when its pull request merges**: the next version's branch cut in that directory starts from a merged base and carries the stale record.
- **The skill text you read may not be the committed text.** Live copies sit in `/root/.hermes/external_skills/<n>/`, synced from `aivara-se/.agents` at some moment, so a sync can carry an edit no commit held. Diff one against `git show origin/main:skills/<name>/SKILL.md`; a difference is a finding for the operator, and a pull request against `.agents`.
- **A fact you cannot find is usually a stale clone.** A second checkout can sit beside the canonical one (`~/github/<repo>` next to `~/github/aivara-se/<repo>`), and the shorter path reads as authoritative while being far behind: `git status -sb` printing `behind N`, an upstream reading `[gone]`, or `git remote -v` answering one URL from two directories. A branch you cut inherits it, so run `git switch main && git merge --ff-only origin/main` before `git switch -c`.
- **Before re-deciding a built rule, read the conversations.** `session_search` reads the mechanism that actually ran and the machinery piled up beside it. FTS5 ANDs every term, so a multi-word query returns nothing where `OR`, a quoted phrase or a prefix (`deploy*`) finds it. A class of cases out of scope means deleting the parts that existed only for them.
- **Diagnose a delivery failure from the headers before reading code: the webhook's content type is the first suspect.** `content_type: form` posts the body as `application/x-www-form-urlencoded` (`payload=<urlencoded JSON>`), and a JSON-only receiver — the service does `json.Decode` — answers `400` before the allowlist can drop an event, the `ping` included. The HMAC is over the raw bytes, so the tell is `Content-Type` in the pasted request; the fix is the webhook (`content_type: json`), not the receiver.
- **Never edit another agent's profile or resources.** Its roster file is the whole identity; a change is its own pull request.
- **A shared skill is a file in another repository.** Every directory under `skills/` in `aivara-se/.agents` is read through `skills.external_dirs`, so a lesson for one is a branch, commit and pull request there. A cleanup or audit request is a read-only pass: `references/skill-audit.md`.
- **Out-of-scope drift is a finding, not an errand — unless the change points at it.** Name the stale copy and offer it; do not quietly widen the pull request. When your text sends the reader to a stale document, the pointer makes that line this change's to fix.
- **In `aivara-se/.agents`, measure the wrap before matching it.** `skills/**` are one line per paragraph, while `agents/*.md` hard-wrap mid-sentence at about 100 columns. Print line lengths (`awk '{print length}'`) before editing, and do not reflow a neighbour. The `writing` skill bans hard-wrapping, so name which it is and leave the choice to the operator.
- **A card is a copy, and the code is written from it.** A card restating a rule of the changed document gets implemented with the old rule unless edited too. `Backlog` cards are still specs, so the body is editable (`gh issue edit <n> --repo aivara-se/<repo> --body-file <f>`, then read it back).
- **Do not turn a temporary card spec into repository documentation.** Move each package's slice to its owning card, preserve the exported names and done checks, and verify no document changed. Remove the obsolete card only after the replacements are readable and the issue closed; a deleted project item leaves the issue, and closing alone leaves clutter.
- **Preserve dependency direction when splitting a card.** Put the direct blocker on every blocked card and the matching `Blocks` list on the prerequisite, then enumerate the project and verify the graph.
- **A card bound to an agent's own account is not board-shaped.** A `Refined` card is built by whichever builder is free — MeMe or MiMi — so a task bound to one account's credential lands on the wrong agent three times in four, and a repository owned by MaMa or MoMo has no `Refined` path. Deleting a repository also needs the `delete_repo` scope, which the agent tokens lack. Leave it in `Backlog`, held by the refiner, the operator step named.
