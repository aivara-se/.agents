# aivara-se workflow

The recurring shape of a change in this organisation: find the one document that owns the fact, edit it, sweep the copies other repositories keep, and land it by pull request. Most of the cost is in the sweep, not the edit.

## Where things live

- Repositories clone to `~/github/<owner>/<repo>`; the organisation's code is `aivara-se/<repo>`.
- **A new repository starts with its product document.** `references/new-project.md` is the bootstrap: create the repository, align its settings, check the ruleset, land `PRODUCT.md` alone, then add `SYSTEMS.md`, the ADRs and the entry file in that order.
- `aivara-se/.agents` is the fleet's shared configuration: `agents/<bot>.md` is that agent's whole identity — its title, the role it owns, its boundaries — and the source of truth for what an agent is; `skills/` is what every agent reads; the donor entry file another repository copies is the `aivara-se/.template` repository, not a path inside `.agents`. The live skill set is the directories on disk (`find skills -name SKILL.md`), never a list written down here.
- A repository on the convention carries **no copy of the skills** — no `.agents/skills/`, and no `## Agent Skills` section in its `AGENTS.md`. Every agent reads them from `~/github/aivara-se/.agents/skills` through `skills.external_dirs`, so a copy would be a second version of the same text, frozen at the day it was made. The organisation's repositories are in that shape. The live set is what `gh repo list aivara-se` answers — treat any list written down here as stale, and enumerate rather than trust it.
- **The entry file says what the service is, once, and carries no provenance.** The operator reviews `AGENTS.md` against this: the template's overview paragraph goes when the map in **Repository Structure** already says it, and the "This file is the `aivara-se` agent convention, version N, adopted from …" line goes because the template and the commit it came from are named in the pull request and the commit instead.
- **The release standard is a process, and each repository carries its own workflow.** `aivara-se/.github/docs/RELEASES.md` states the steps and the rules a publish run keeps — read the version file, stop when the version is tagged and released, build, tag after the builds, release, then the registry when applicable. The YAML is per repository: `.github/workflows/publish.yml` in each, inlined, so a change to one artifact's packaging lands in that repository alone.
- **Treat board scope and repository scope separately.** To act on a board column,
  enumerate project items and filter by the exact `Status` value, resolving each
  item's issue URL; do not substitute `gh issue list`, because open issues can
  be outside the board or in another column. For destructive requests, confirm
  whether the user means delete the issue, close it, or remove only the card
  before acting. Writing one — creating the issue, adding it to the project,
  setting its column, claiming it — is `references/board-project.md`, with
  project #2's field and option ids and the one-turn card-then-build rule.
- **The wake procedure lives in the organisation's own `dispatch` skill.** `aivara-se/.agents/skills/dispatch` owns what an assignment, a review request, a `changes requested` review, a failed check and a mention each mean, and how a pull request is opened and answered; it is read by every agent through `skills.external_dirs`, not copied here. This skill carries the other half — where a fact lives in a repository, the sweep across copies, the gate, and the landing. When a change starts from a wake, read that skill for the loop and come back here for the repository work; do not restate its rules in this file.
- Mail: `himalaya` reads the shared account as `-a aivara`; the envelope list is often where a merged-change notification lands first.

## Doing the change, in order

1. **Fetch before believing a checkout, and read the fetched ref, not the working tree.** A clone is a snapshot and is never auto-fetched. Run `git fetch origin` in the target repo, then `git log --oneline origin/main`, `git branch -r` and `gh pr list --repo aivara-se/<repo> --state all`, before cutting a branch and before editing — a pull request already open on the same decision is the change to review, not a second one to open, and a remote branch named for the change with no pull request yet is still work in flight — and before quoting any file: `git fetch` moves the refs and not the files, so a document read from the working tree afterwards is still the pre-fetch text. Read `git show origin/main:<path>`, or fast-forward with `git checkout main && git merge --ff-only origin/main`; `git branch -vv` printing "behind N" is the tell, and so is a document whose version sentence contradicts the commit subjects in `git log --oneline origin/main` — that contradiction means the text you just read is the pre-fetch tree, not the repository. For a gate run, clone `https://github.com/aivara-se/<repo>` rather than the local checkout — a clone of a stale clone is stale, and it passes the gate on a tree that is not `main`. A fact you cannot find has usually merged after your clone rather than never existing.
2. **Name the owner of the fact.** Before writing about an agent's role, read `aivara-se/.agents/agents/<bot>.md`; before writing about a service, read its `docs/PRODUCT.md` and `docs/SYSTEMS.md`. Never write a role or a convention from memory or from a draft.
3. **Sweep the copies on the fetched refs, hidden repositories included, and sweep for the rule as well as the value.** `search_files` is ripgrep-backed and skips dot-directories, so a pass over `~/github/aivara-se` silently misses `aivara-se/.agents` and `aivara-se/.website` — the two that carry the agent roster. Run `git grep -niE '<old wording>' origin/main` inside each clone, or point `search_files` at the hidden repository's own path. A fact with one home is still restated in other repositories' documents, site copy, dictionaries and the board's cards; every hit is stale. A roster role is the worked example: `agents/<bot>.md` owns the title, `.website/src/lib/i18n/en.ts` carries the role line each card and page prints, and `.website/PRODUCT.md` states the rule the line must satisfy (its word count, its voice). Sweep for that rule too — a rename that changes the value's shape (a five-word phrase becoming a two-word title) leaves the product document asserting a constraint the copy now breaks, and no search for the old wording reaches it.
4. **Classify blockers before asking.** Separate operator-owned files or decisions from edits you can make yourself. Proceed with every independent fix; ask only for the smallest genuinely unavailable input, and name the exact path or decision that is waiting. Do not turn a review finding into a question when the repository and its issue/spec provide enough context.
5. **Synchronise the work item before coding.** If the implementation or documentation pass discovers a missing acceptance rule, update the associated issue/spec in the same workflow, then read it back and verify that the new rule is precise. Cards are executable specifications: leaving an ambiguous rebuild, restart, or ownership rule in the card recreates the stale design in the next change. If a design card is being removed, first partition its rules into the implementation cards that own them, edit those cards with only their relevant interfaces and done checks, read every edit back, then close the source issue and remove only its project item. Keep repository documents untouched when the user explicitly makes the cards the temporary specification.
6. **Make the smallest edit that removes the stale claim.** Match the document's own register and the `writing` skill's rules. Where the change turns on a new distinction, state both halves, and keep a negative rule negative ("this agent is never assigned a card") rather than an aside.
7. **Verify before opening the PR.** Run the repository gates — in a bun repository `bun install --frozen-lockfile` first, because `bun x tsc` alone fails with `TS2688: Cannot find type definition file for 'bun'`; in this sandbox `/tmp` is noexec, so a Go gate is `mkdir -p $HOME/tmp && TMPDIR=$HOME/tmp go test ./...`, or every package fails `fork/exec … permission denied` — then `git diff --check`, and targeted documentation checks such as relative-link resolution and stale placeholder searches. Report empty or no-package checks accurately; never convert a skipped gate into a green claim. A workflow file is a gate of its own: run `actionlint <path>` on every workflow the change touches, because a workflow that does not parse never runs — GitHub's expression language has no `replace()`, so a name assembled with it is rejected at load while the YAML reads as valid. A green run is not proof the branch you meant ran: a job whose `if:` is false reports success without executing, so read the run's own log for the line it took (`gh run view <id> --log | grep -i 'nothing to publish'`) and the artefact it claims (`gh release view <tag> --json assets`) rather than inferring either from the check.
8. **Land it by pull request, never on `main`.** When the operator asks this agent to open the PR, do the full branch, commit, push and `gh pr create` sequence yourself; do not hand the delivery to Root or another agent unless delegation is explicit. When the operator instead asks for a contribution to a peer's open pull request, push one focused commit to that head, comment the sha and what it changes, and leave the review to the operator; a stacked pull request or a verdict on a commit of yours is the wrong shape. Branch `docs/<slug>` (or `feat/`, `fix/`), commit with a typed lowercase subject (`docs:` then an imperative phrase), and a body saying what changed, why, what was verified, and what is deliberately out of scope. When the organisation is mid-restart, the base is the restart branch and not the default — `gh pr create --base next` — and the `Baseline` ruleset that makes a `main`-based pull request wait on a peer approval guards `main` alone: a pull request based on the restart branch reports `mergeStateStatus: CLEAN` with no required review, so read `gh pr view <n> --json baseRefName,mergeStateStatus,reviewDecision` before calling it blocked. Request review from the operator (`thani-sh`), and from one peer agent (`thani-sh-meme`, `thani-sh-mimi`, `thani-sh-momo`) when the change is implementation. A documents-only change — the product document, the system document, an ADR, a README that describes behaviour — is reviewed by the operator alone: the operator reads product and architecture level, the peers build and review code, so a peer on a design pull request answers with line-level findings that lengthen the document without settling a decision. That is a standing rule of the operator's, not a default to re-derive: `reviewRequests` on a design or architecture pull request reads `["thani-sh"]` and nobody else, and it is read back to prove it. **The reviewer the operator names classifies the artifact.** "Add only me as a reviewer" says documents-only, so a request that would also need new workflow YAML stays a document: shipping the YAML is an implementation change that owes the peer review the instruction just ruled out. Name the unbuilt mechanism in the body as out of scope. `gh pr create --reviewer` can report a failure after the pull request already exists, so re-apply with `gh pr edit <n> --add-reviewer <login>` and read `gh pr view <n> --json reviewRequests` back before believing the reviewers are set. **Every push re-requests review.** A push leaves the decision, the block and `reviewRequests` where they were — a submitted review empties the request list, and a new commit does not put it back — so after every push, not only one answering a review, run `gh pr edit <n> --add-reviewer <login>` for whoever the change's reviewer list is — the operator alone on a design pull request, the operator and one peer on an implementation one — and read `gh pr view <n> --json reviewRequests` back. A fix commit does not answer a reviewer by itself either: read the findings on the review's own surfaces — `gh api repos/<owner>/<repo>/pulls/<n>/comments` for inline comments and `pulls/<n>/reviews` for the verdict, because `gh pr view --comments` lists the conversation and misses them — then post a comment mapping each finding to the commit that fixed it, or the pull request waits on a reviewer who was never asked again. **A push also falsifies the body.** A later commit that lands what the body listed as out of scope, widens the files it says changed, or drops a claim it made leaves the description lying to the reviewer it just re-asked; re-read the body against `git diff origin/main` after the last push and rewrite it in the same turn. Answer a finding by changing the record it named — and an older ADR is immutable, so a clause the decision falsifies is answered by a new ADR that names the clause it overrides, never an edit to the merged record and never a clause left asserting the opposite. The merge is a standing act of this agent's: an approved, clean pull request — checks green, `reviewDecision: APPROVED`, `mergeStateStatus: clean` — is MaMa's to land, the operator merging by hand only while the service is not live to wake her for it; a peer asking in the pull request for the merge is asking her. **The approval can never be this agent's own**: the `Baseline` ruleset requires one approving review and GitHub refuses a self-approval, so a pull request this agent opened sits `mergeStateStatus: BLOCKED` / `reviewDecision: REVIEW_REQUIRED` until the operator or a peer approves it — report it as waiting on that review and hand it back, never force it and never treat "merge it" as doable when the author is you. Grade a red check against the ruleset's *required* list before calling it a block: `gh api repos/<owner>/<repo>/rulesets/<id>` names the required checks, and a check the ruleset does not require leaves the pull request `mergeStateStatus: UNSTABLE` — still mergeable — where `BLOCKED` is a required thing missing (the review, a required check). A language's code-scanning analysis that fails only because the branch carries no source for it (a restart that deletes the code) is the repository's own setup and not the diff: report the settings change as the operator's and let the change land when nothing requires that check green. **Merge with the method the repository allows**: a repository enables one method and refuses the others, so read `gh api repos/<owner>/<repo> --jq '{squash:.allow_squash_merge,rebase:.allow_rebase_merge,merge:.allow_merge_commit}'` before choosing the flag — the repositories here are set rebase-only where read, and refuse a squash merge outright. A rebase merge lands every commit the branch carries, one by one, so a review-fix commit lands beside the original: keep each commit on a pushed branch final. **A pull request that lands a long-lived restart branch proves it reverts nothing before merging**: `git merge-base --is-ancestor origin/main origin/next` — false means `main` gained commits after the fork and the merge silently drops them, so rebase the head onto `main` and re-run the gate before landing it. Read `delete_branch_on_merge` in the same call (`--jq '{squash:.allow_squash_merge,rebase:.allow_rebase_merge,merge:.allow_merge_commit,delete_branch:.delete_branch_on_merge}'`): with it on, the merge deletes the head branch, so landing a pull request whose head is a branch meant to outlive it (a long-lived `next`) removes that branch — raise the setting with the operator before merging, or recreate the branch at the new head afterwards and say so in the report. **Report the link whenever a pull request is opened** — in this organisation or any other repository this agent works in — by putting its URL in the same turn it is created, without being asked; the operator wants the link, not a summary they have to hunt it out of.
9. **Report the ripple.** Name the other repositories and cards still carrying the old fact, and any decision the change leaves open — as follow-ups, not as silent scope. Where the change arrived as a chat request rather than a card in `Backlog`, say so: the board is the record, and an unrecorded change is a gap to offer to close. A merge that closes a card ripples into text nobody asked you to touch: read the repository's open pull requests for that number before merging, because a body or a document that names the card as open is stale the moment it closes — land the text-only ones in the order their lines depend on, and correct a line of your own rather than leaving it for a reviewer to find.

## Handing implementation to a peer agent

When the operator asks for a prompt to give a builder — MeMe, MiMi or another agent — start from `templates/handover-prompt.md`: the repository's documents are the specification, the design is frozen, the work lands as one pull request, and the builder stops and asks on a blocker rather than deciding one. Name the gate and the acceptance checks in the prompt, and list the values only the operator knows (a host path, a roster, a credential) as questions to ask, not as values to guess.

## A pass over the state: built, in flight, waiting

A status request is answered from the board and the code, never from the cards' prose. Enumerate both sides, diff them, and prove what you can.

- **Enumerate the board and the open issues separately.** `gh project item-list <n> --owner <org> --limit 200 --format json`, parsed in code because the listing truncates in a terminal, gives every card's exact `Status` — read it as `item.get('status')`, because a card sitting in no column carries no `status` key at all and `item['status']` raises `KeyError`; a status that is empty where the operator said they moved the card is a finding to name, not a no-op to pass over; `gh issue list --state open --repo aivara-se/<repo>` gives the repository's side, and `gh search issues --owner aivara-se --state open` covers every repository at once when the question is the organisation's, so the one issue a per-repo listing hides is still named. The two sets differ by design, so an open issue carrying no card — and a card whose issue is closed — is a finding to name, not to tidy away. Before calling a card-less issue a gap, read its timeline (`gh api repos/aivara-se/<repo>/issues/<n>/timeline --paginate`) for `removed_from_project_v2`: an operator who removed the card deliberately is saying the card is not the unit of work for it, which is a different finding from a card that was never added.
- **Run the repository's own gate yourself, at remote's head.** Clone the remote URL and run `gofmt -l .`, `go vet ./...`, `go test ./...` on the SHA you are reporting; a green CI run on that same SHA is the second opinion. If one run fails and repeats pass, report it as a flake with the test's name — never as a red `main`.
- **The board moves while you work.** Re-read it before writing the report and put the moment on anything that changed mid-pass ("moved at 16:32"), because the operator moves cards by hand and nothing wakes the agents a move would awaken until the service is live; a `Status` you set to match the operator's stated move is theirs to overwrite within the same hour, so report the column at the moment of the read and never re-apply your edit over their hand. Grade each card against its column's rule: a deploy, cutover or acceptance card sitting in `Refined` is written into a builder who cannot do it, and a card whose blocker has closed without moving is a wake that never came.
- **An assignee is a claim, not a run — the service never moves a card.** In the board flow, the service writes one field, the assignee, and starts that agent's run; v1 carries no board flow and makes no such write. the move from `Backlog` to `Refined` is the refiner's act inside that run and nothing else, so "assigned to MaMa" is the service's last act on a `Backlog` card, never a stalled step. A card sitting in a column under an agent's login is therefore one of three states the column cannot tell apart: legitimately held because it waits on the operator, assigned by a hand rather than by a claim, or a claim whose run never went. Answer "why is this card not moving" from the card's own prose plus its timeline (`assigned`, `unassigned`, `project_v2_item_status_changed`, each with `actor` and `created_at`) — the prose says why it is held, the moments say whether a run had a chance to move it. Where every write carries one login (the board token's owner), the timeline renders the service's writes and an agent's hand-moves as the same actor, so name that the board cannot separate them rather than asserting which one moved the card.
- **No inbound delivery, no look.** The service acts only when a delivery arrives, a run it started ends, or at boot — there is no clock and no polling. Until the organisation webhook is registered, a newly added card generates no delivery and can sit unassigned in `Backlog` for tens of minutes before the first look claims it; check whether the webhook exists before grading that as a fault. And once the service has written the assignee, that card is treated as claimed and is never woken again — a claim whose run did not start is repaired only from memory, so a restart makes an assigned-but-never-run card indistinguishable from one being worked.
- **Grade a `Finished` card against its own *Done means*, not its column.** Read the issue's timeline (`gh api repos/aivara-se/<repo>/issues/<n>/timeline --paginate`, filtered in code to `project_v2_item_status_changed`, `closed` and `commented`, each with its `actor`) and its comments: the operator's hand-moves show the actor and the moment, and a card closed with nothing said under a card that demanded its evidence on the thread is a claim, not a delivery. A deploy, cutover or acceptance card leaves artefacts the tree can prove — the host facts recorded, the "provisional" wording gone, the latency frozen in the acceptance section, the sentence the card said to verify or drop — so check those before reporting the work done and name which of the card's own checks nothing in the record answers. The one artefact no tree can carry (the organisation webhook) is the operator's to confirm, not a liveness claim to infer from the column.
- **Grade a branch against the default, not in place — a restart branch is a spec, and its deletions are owed decisions.** When asked to check a branch that is not `main` (a `next`, a rewrite), fetch every head (`git fetch origin '+refs/heads/*:refs/remotes/origin/*'`) and read that branch's tree and `git log --oneline origin/main..origin/<branch>` before opening any file: a plain `git fetch` moves the refs and not the working tree, so the files you read still show `main`, and you must read `git show origin/<branch>:<path>`, not the checkout. Walk the diff both ways. A `nuke!`-style commit that deletes the implementation leaves the surviving documents as the whole specification, so grade each surviving rule against them — and check every rule the documents still assert against the decisions that were deleted with the code. An acceptance criterion the new scope keeps (dedup, an unsigned request rejected, no logged body) whose ADR went in the nuke is **unrecorded, not settled**: list the deleted decisions the new flow still needs, rather than resurrecting the old files verbatim — they named the mechanism the restart dropped, and a trimmed decision keeping the old mechanism's name is a contradiction inside the restatement. Name the surface the new docs leave interface-less (a flow whose roster or allowlist nothing now defines) as the thing to settle before a builder can start. When the operator confirms a restart by saying which decisions to ignore, treat the deleted ones as abandoned rather than lost: do not resurrect them, and leave the number the operator said their next decision takes — do not open a fresh ADR into it. A fact the operator fixes that the new flow needs but no document carries (the service's name, its scope, the agent roster) goes into the product document as the operator-facing surface, with the pull request body saying the file's format is still unrecorded and whose decision it is.
- **Prove a suspected drift with a probe, not an argument.** When the finding is "the record and the tree disagree", write the throwaway test in a scratch clone of the remote — never in the repository — after reading that branch's own test helpers for their current signature, and report its output; a reproduced gap needs no debate. After an aborted merge test, `git reset --hard <ref>` then `git clean -fd` (`git checkout -- .` refuses while paths are unmerged, and the clean takes the probe with it, so write it after the reset).

### Answering "what is left before it runs live"

A pre-launch question is a readiness pass, not a status pass: the answer is the work between the tree and a first real run, and it is a list grouped by whose hands each step is in — the agent's, the operator's, the host's — never one undifferentiated backlog.

- **Read the launch card's own steps and *Done means*, then grade the tree against them.** The card that owns the cutover enumerates its sequence (build, unit, proxy, webhook, first delivery, a checklist of facts to verify-or-drop); walk it and mark each step done, waiting or unstarted. A `Finished` card named in that sequence, or a blocker already closed, is a step that has moved on.
- **Enumerate the artefacts the documents claim the repository holds and check the tree for them.** A services doc that asserts "the config file is committed to this repository" while the tree carries only a test fixture is a gap the launch needs closed, not a settled fact — read the claim, then `git ls-tree` for the file. A sentence worded as a future promise — "provisional until the deployment lands", "the first live run freezes this" — marks work only the live run completes; list it as remaining, and expect the launch to freeze those numbers.
- **Name an open defect the launch card does not list as a blocker, and say whether it blocks the test or is an accepted gap.** A card sitting in `Backlog` with no assignee and no `blocked_by` edge is exactly the one a readiness list silently omits.
- **Authoring the missing artefact: take every fixed value from the documents or the loader, and surface the one judgement call.** A committed config's shape is the loader's schema and the services doc's list, not the example fixture — read both. A value the documents do not fix (an allowlist, an interval, a scope) is a decision the operator owns: pick the reading that makes the documented behaviour true, say so in the pull request body as the one thing that would change your mind, and name the one-line revert. Prove the file loads with the project's own loader in a throwaway test beside the real one and delete it before the commit — `gofmt`, `go vet` and `go test` say nothing about a JSON file nothing imports, and hand-checking JSON validity is not the loader's verdict. A new file at the repository root goes into the entry file's *Repository Structure* map in the same pull request — but not plumbing whose purpose is obvious (`go.mod`, `.gitignore`, a conventional workflow path), which only bloats the map and tells a reader nothing. The map is a path list for what a reader has to discover, and a path it does not carry leaves the map incomplete the way a stale one leaves it lying.
- **Separate the hands explicitly.** Steps that need systemd, Caddy or a shell on the host are the operator's and Root's, not reachable from an agent sandbox — say which steps are the agent's own (author and land a missing committed config, merge a pending docs fix) and offer to do them, rather than listing them all as one block.
- **A host handoff is an artefact, not a description, and it names the two traps a user unit sets.** Hand over the unit file, the environment-file shape (the secret values, mode `600`; the committed config carries only their names) and the proxy site, with the host paths left as placeholders for Root to fill rather than guessed. `loginctl enable-linger <user>` or the unit dies with the operator's last session; and a user unit's `PATH` is minimal, so a service that spawns another binary as a child needs that binary's absolute path passed in on a flag — the bare command resolves in your shell and not in the unit, and the first wake is what fails.

## Deciding and recording an architecture change

`references/design-decisions.md` is the loop: ground in the documents and the past attempts, answer with options first, take a default on every fork that does not change the artifact, record the pick as an ADR before the code, and sweep the documents it falsifies in the same change. That file also carries the operator's expectations for the shape of the answer, the conflict pass that rereads the edited documents against each other before the pull request is opened, and *Probing a behaviour a decision turns on* — the recipe for an external claim that would otherwise be written as "unrecorded here". Its *Containerising a service that drives the host* section sorts processes by what they touch and names the three shapes available to one that spawns the host's binary. Its *Planning ahead across versions* section answers a request to plan vN+1 onward — options first, one increment per version, what is out and the invariant it costs — and says when the plan is recorded into the product document rather than left in chat. A candidate that would have to stop a run already in flight dies there: a wake starts a new run and is not a message to the one working.

**The deliverable is the record until the operator asks for code.** A chat request for "the next version" is a design pass: land the ADR and the documents it falsifies as a docs-only pull request, and name the implementation — the code branch, the tests, the webhook or host setting it needs — as out of scope in the body. Do not start the code from the same request; if it is genuinely ambiguous, ask, because a docs-only pull request is cheap to extend and an unwanted implementation is not.

**An ADR stands alone.** It cites only earlier ADRs, never `PRODUCT.md` or any other document that moves with the version; the documents link to the record, never the reverse. `references/design-decisions.md` carries the rule at the point the file is written.

**A follow-up "would X be simpler?" is answered with the mechanism test, not a rewrite.** Say what the proposed structure owes — a lifetime bound, a kill path, a boot reconcile, a queue that spends one run per item — what the repository's own deleted tree already priced, and what would change the recommendation. When the answer holds, add one precision clause to the ADR so the next reader cannot mistake the small structure for the heavy one, and put the rejected candidate in the pull request body; then push, re-read the body, and re-request review, because a push empties the request list. A second ADR for a fork that changed no decision is the accretion the directory cannot carry.

## Refining a card in `Backlog`

A card is refined when it is feasible, complete, and unblocked. Feasibility is a read of the code and the documents it builds on, not of its prose: a card whose premise names a surface that exists only on an unmerged pull request cannot start.

- **A card that cannot start stays in `Backlog`, with its blocker linked.** Moving it to `Refined` hands it to a builder against a surface that is not on `main`. Link the prerequisite with the native `blocked_by` edge (the `github` skill's *Sub-issues and Projects v2*), as the org's cards do, and say it in the card's prose too.
- **A removal card is refined against the code's readers, not its prose.** Grep for who *reads* the surface, not who names it — `audit.Open` being the only opener, and no document consuming the file, is what made the service's dead-letter removal sound — then find what that surface was the only *writer* of, because a record with no other home disappears with it: a failed look that woke nobody appended no audit line, so the miss file was the only record of its refusal, and the card had to say the refusal stays an audit line and the reason goes to the service's stderr.
- **Keep the refiner's assignee on a refined-but-blocked `Backlog` card.** The claim is what stops the next look waking the refiner for a card already refined; a `Backlog` card with no assignee is woken again after every restart. The merge that clears the blocker wakes the refiner for the blockers it cleared, and that is the act that moves the card on.
- **A `Refined` card carries no assignee.** The rule wakes a card in `Refined` only when nobody holds it, so the move from `Backlog` clears the refiner's own login in the same act; leaving it strands the card. An assignee in `Refined` or `Started` also holds that agent's slot.

## Pitfalls

- **A documents-only pull request that has grown review-fix commits is reissued from a clean branch, not stacked further.** A rebase merge lands every commit the branch carries, so the third fix commit reads as churn beside the design it corrects, and each round answers line findings with more defensive prose until the change is twice the size of its decision. Once a design pull request has taken more than its first round of review fixes, close it with a comment saying what it supersedes and why (`gh pr close <n> --delete-branch --comment …`), and open one fresh commit from `main` — the same decisions in leaner text, reviewed by the operator alone. A decision that inverts before any review is reissued the same way: the branch would otherwise carry the record written and then replaced, and a rebase merge lands both commits. Rewriting the open branch is not the alternative: the branch has been seen, so it cannot be force-pushed, and a push cannot retract a commit.

  **Do not stack a design pull request on another unmerged design pull request's branch.** Both edit the same lists — a Roadmap, a *Planned, not built* section — so the base branch keeps growing, the stacked diff stops being reviewable, and a merge or a re-request on the base rewrites the stacked branch's history under the reviewer. Cut one branch from `main` for the batch, or hold the second until the first lands; when only the ordering forces a stack, say so in the body and expect to reissue. **A reissue at a named commit is written, not cherry-picked**: `git checkout <commit> -- <paths>` onto a branch cut from `main`, then commit it under the agent's own identity, because a cherry-pick carries the original author and committer forward and puts the operator's name on commits in a pull request that is theirs to approve. Prove the cut with `git log -1 --format='%an <%ae> | %cn <%ce>'` and `git diff --stat origin/main` before pushing.

- **`AGENTS.md` is the operator's file: name its stale lines, and edit it only on the turn the operator asks.** The protection is a convention, not a guard — an edit can land from a background run, which is exactly why the discipline is the agent's — so silence is not consent, and a design pull request that leaves the file stale says so in its body. When the operator does say update it, edit it on the same branch, re-run the link check and the gate, and correct the pull request body that said the file was theirs. Its *Current Project Focus* is the section that goes stale first: it is written before the code and is "replaced rather than appended to", so the pull request that lands a phase leaves the previous phase's steering standing — and a reviewer working a card will name that drift and leave it out of scope. Treat it as a finding with no owner and put it in the report: three clauses go stale together when a build phase lands, and one small pull request fixes all three — the *Current Project Focus* (rewrite it to name the cards that are open and nothing that is `Finished`), the check note (the gate in the future tense, and any "until the packages exist there is no code to check" clause), and the *Repository Structure* map (a path list that still reads "once the code lands" is a map that lies, and the map's own rule is to fix it in the same pull request as the code that made it true). When the operator scopes a change to one file, that repair is the next pull request: name it in the first body and land it as soon as the merge lands.
- **A repository rename is a stale fact with many copies, and the local clone hides it.** GitHub redirects the old URL, so an existing clone's remote keeps fetching through the redirect and never shows that the name moved; the directory stays under the old path (`~/github/aivara-se/<old>`) and `git fetch` there succeeds, which is why the drift survives. Enumerate current names with `gh repo list aivara-se`, and read `gh repo view <owner>/<old> --json name`: it resolves the redirect and answers the new name (a repository renamed to a dot-prefixed name answers under the new one, `org-website` → `.website`). A clone made before the rename keeps the old directory, and a fresh clone of the new name sits beside it as an apparent second repository — `git remote -v` printing a URL that disagrees with the directory name is the tell that the two are one repository, not two. The old name is restated past the documents: the Go module path, the binary and its `cmd/` directory, the committed config's filename, the environment-variable prefix (`<NAME>_*`), and every other repository's project lists, links and test fixtures. Sweep the organisation for the old name and name the copies you did not touch.
- **A `nuke!` reset deletes the front door, and the reset's parent commit still has it.** A repository restarted from scratch loses its `AGENTS.md`, `README.md` and committed config in the reset, but `git show <reset-commit>^:<path>` still answers each one — with the adopter's filled convention slots, its house rules, its gate and its structure map, and the convention version it last took. Read them before writing replacements rather than filling the template `AGENTS.md` from scratch, then drop what the restart invalidated: a house rule bound to the mechanism that was abandoned (a board write, an API client) is rewritten, not carried.
- **A document a test loads is pinned to the code, not to the design.** A repository can run the README's example configuration through its real loader (`TestReadmeExampleIsLoadable` with `DisallowUnknownFields`), so a docs-ahead change that adds a field to that example fails the gate before the loader accepts the field. Grep the test tree for the document path (`search_files` for `README` across `*_test.go`) before editing an example, and leave the runbook's example, its environment file and its event list to the pull request that adds the code — say so in the body as the scope cut rather than describing a configuration the binary refuses. The design documents and the ADR carry v-Next; the README follows the running binary.
- **A decision that replaces a mechanism falsifies the entry file's house rules, and there the operator holds the pen.** Sweep the product and system documents in the change, then read `AGENTS.md` for prohibitions the decision just broke — "never call the API", "hold no credential", "keep no durable state" — and name each one in the pull request body as the operator's turn. Editing them anyway leaves the refusal to the operator; leaving them unnamed hands a builder the old prohibition as policy.
- **A standard that outgrows its first implementation states the steps and the rules, and each repository carries the workflow.** Rewriting a document from one artifact (a desktop app) to a class (npm packages, native binaries, asset bundles) means: the invariant steps in order, the rules every run keeps, and what each repository supplies with a per-kind example (version file, build command, asset names, secrets, registry). Do not factor the YAML into a reusable workflow in `aivara-se/.github` and do not write a *Provided implementation* section that points at one: one packaging shared through a callee makes a change to one repository's build land in all of them, which is the coupling the per-repository file exists to prevent. The standard names worked examples; each repository's `publish.yml` is the only copy of its packaging.
- **A readme-driven README links only paths the tree already carries.** Writing the README before the code is a legitimate instruction, but a relative link to a file that does not exist yet (`docs/SYSTEMS.md`, a workflow) is a broken link a reviewer fails, and a gate command naming a CI workflow nothing runs is a red check waiting to happen. Link the documents that exist, let the pull request body name the artefacts still to come, and add the workflow with the first code rather than as a failing check on a docs pull request.
- **A request that contradicts a written convention is a change to the convention, not an exception to it.** When the task cannot be done without breaking a rule the repository states about itself — a skill that must name another skill, under a "skills stand alone" rule — edit the rule in the same pull request and argue the new wording in the body. Doing the task and leaving the rule makes the tree break what the repository asserts, and the next author inherits a contradiction where a decision belonged. Say in the body which rule moved and why the old one could not hold; a convention change is the operator's to review, not a silent scope.
- **A section a repository has to drop is a stale convention, not a stale repository.** When `aivara-se/.template`'s `AGENTS.md` or `.agents/README.md` still describes what the adopter deliberately left out, the fix belongs in `aivara-se/.agents` as its own pull request; forking the convention per repository is how the five copies drift.
- **Edit a repository from `execute_code` with absolute paths, not relative ones.** The helper runs in the profile's home, not the directory a previous `terminal` call sat in, so `patch('docs/PRODUCT.md', …)` resolves under `~/.hermes`, the soft guard refuses it, and every path in the batch fails the same way. Prefix each path with the absolute clone path (`~/github/aivara-se/<repo>/…` written in full), or do the edit through `terminal` or the standalone `patch` tool in the repository's cwd.
- **The clone is shared with other agent sessions, so the working tree can change between your calls.** Another agent may check out its own branch in the same `~/github/<owner>/<repo>` directory while your edit sits uncommitted, and the branch and `HEAD` belong to whoever last ran `git`, not to you. Read `git branch --show-current` and `git log -1` immediately before every edit batch as well as before every commit — a checkout can land between two of your calls, and a file written into another session's tree disappears from your branch when they switch back — and treat a tool warning that the file changed under you as that checkout having happened. If `HEAD` is not your branch, copy the edited file out, check your branch out, re-apply the change there, and never commit onto another session's detached `HEAD`. Put the tree back on the branch you found it on when you are done, so the other session's next command is not run against yours. When the checkout is on another session's branch and the work is documents-only, `git clone https://github.com/aivara-se/<repo> /tmp/<repo>-docs` and work there instead: the shared tree is left exactly as found, the branch is cut from the remote's head, and the gate still runs on that head — a throwaway clone costs one command and removes the whole class of interference. To contribute to an existing pull request's head, use a worktree under `$HOME` instead: `git worktree add -B <branch> <dir> origin/<branch>`, commit and push from there, then `git worktree remove <dir>`; the shared checkout stays on the branch it had, and `/tmp` is noexec. **And the wake races you once the service is live.** A pull request this session opens wakes a fresh session for the same agent on a review finding, and that session may push the fix, arm auto-merge and land the pull request while you are still editing: read `gh pr view <n> --json state,commits,reviews` and the remote head before pushing a fix or opening the change again, because a push to a branch another session already moved is rejected and leaves an orphan commit, and a second pull request for the same decision is the duplicate the fetch-first step exists to prevent.
- **The skill text you read may not be the text the repository carries.** The fleet's live copies sit in `/root/.hermes/external_skills/<n>/` and are synced from `aivara-se/.agents` at some moment; a sync can carry an edit that no commit in the repository ever held, so the rule every agent reads has no record. Before quoting a shared skill in a comment or a pull request, diff the live copy against `git show origin/main:skills/<name>/SKILL.md`; a difference is a finding for the operator and a pull request against `.agents`, never an edit here.
- **A fact you cannot find is usually a stale clone, and one repository is often cloned twice.** The change merged and your tree predates it — fetch before concluding it does not exist. Worse, a second checkout can sit beside the canonical one (`~/github/<repo>` next to `~/github/aivara-se/<repo>`), and the shorter path reads as the authoritative one while being dozens of commits behind: `git status -sb` printing `behind N`, or `git remote -v` answering the same URL from two directories, is the tell. Read both, and author from the one whose `origin/main` is the head you are about to branch from — writing a change against the stale copy means writing against text the repository already replaced.
- **Before re-deciding an interface or an acceptance rule the organisation already built, read the conversations, not only the repositories.** `session_search` reads sessions the repositories do not keep — the mechanism that actually ran, and the machinery the design piled up beside it. FTS5 ANDs every term, so a multi-word query returns nothing where `OR`, a quoted phrase, or a prefix (`deploy*`) finds it. The recurring lesson is that the mechanism was sound and the weight sat beside it: when the operator puts a class of cases out of scope — restarts, crashes — delete the parts that existed only for those cases instead of re-deriving them into the next design.
- **Diagnose a reported delivery failure from the delivery's own headers before reading code: the webhook's content type is the first suspect.** A GitHub webhook configured `content_type: form` posts the body as `application/x-www-form-urlencoded` (`payload=<urlencoded JSON>`), and a JSON-only receiver — the service's does `json.Decode` — answers `400` on the body before the allowlist can drop an event it does not act on, the `ping` handshake included. The HMAC is over the raw bytes, so the signature verifies either way and the tell is `Content-Type` in the pasted request; the fix is the webhook (`content_type: json`), not the receiver. Reproduce the exact payload in a scratch clone (see *A pass over the state*) before touching the service, and confirm with the operator that a code change is still wanted once the configuration explains it.
- **The restatements live in other repositories.** Enforcing a fact in the one repo you were asked about leaves the sites and dictionaries lying; search the organisation, then say which files you did not touch.
- **Never edit another agent's profile or resources.** Its roster file is the whole identity; a change to it is its own pull request.
- **A shared skill is a file in another repository.** Every directory under `skills/` in `aivara-se/.agents` is read through `skills.external_dirs`, so a lesson for one of them is an edit to that repository — branch, commit and pull request it like any other change there. An in-place edit to your clone is invisible to the fleet and is the same second version the repositories were stripped of. A request to clean up, trim or audit the corpus is a read-only pass with its own checks and report shape: `references/skill-audit.md`, which also carries how the mechanical half lands as one operator-reviewed pull request and which checks the cleanup should leave behind.
- **Do not restate a fact the document already links to.** Say what changed and point at the home; restating is how the copies drifted apart in the first place.
- **Out-of-scope drift is a finding, not an errand.** Name the stale copy in the report and offer it; do not quietly widen the pull request to cover it.
- **In `aivara-se/.agents`, measure the wrap before matching it.** `skills/**` are one line per paragraph, while `agents/*.md` hard-wrap mid-sentence at about 100 columns; `README.md` and the root `AGENTS.md` are mixed, with single lines past 200. Print the file's line lengths (`awk '{print length}'`) before editing rather than trusting a column count, and do not reflow a neighbour as a side effect. The `writing` skill bans hard-wrapping, so a hard-wrapped file is either a deliberate SOUL-file exemption or the corpus contradicting itself — name which and leave the choice to the operator.
- **A card is a copy, and the code is written from it.** A card whose text restates a rule of the document you changed — a router, a config, a template — gets implemented with the old rule unless the card is edited too. Cards in `Backlog` are still specs, so the body is editable (`gh issue edit <n> --repo aivara-se/<repo> --body-file <f>`, then read it back); the board-flow service writes only the assignee.
- **Do not turn a temporary card specification into repository documentation.** When the user asks to move a frozen interface or acceptance surface into implementation cards, distribute each package's slice to its owning card, preserve the exact exported names and done checks, and verify that no document was changed. Remove the obsolete project card only after the replacement cards are readable and the issue is closed; deleting a project item alone leaves the issue behind, while closing alone leaves board clutter.
- **Preserve dependency direction when splitting a card.** Put the direct blocker on every blocked replacement card and the corresponding `Blocks` list on the prerequisite card, then enumerate the project and verify the resulting graph; relying on prose order makes parallel work start against an incomplete interface.
- **A card whose work lives in an agent's own account is not board-shaped.** A `Refined` card is built by whichever builder is free — MeMe or MiMi — so a task bound to one account's credential (deleting that account's repository, say) lands on the wrong agent three times out of four, and a repository owned by MaMa or MoMo has no `Refined` path at all. Deleting a repository also needs the `delete_repo` OAuth scope, which the agent tokens do not carry (`gist, project, read:org, repo, workflow`), so it waits on the operator granting it per account. Leave such a card in `Backlog` held by the refiner, with the operator step named and no sub-issues created: splitting it makes cards nobody can start.
