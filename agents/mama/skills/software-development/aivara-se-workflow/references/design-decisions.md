# Designing and recording a decision

## The loop

1. **Ground before proposing.** Fetch the repository; read the product and system documents, every ADR in `docs/adrs/`, the fleet's shared skills in `aivara-se/.agents` and any open pull request against them, and search past sessions (`session_search`). A change in review can retire a candidate, and a mechanism proposed from memory repeats a withdrawn decision.
2. **Answer with options first.** A numbered list, each option one line plus its single trade-off, ordered by the stated priority. Then say which survive and why the others are out.
3. **Recommend one and take the defaults.** Every fork that does not change the artifact gets a named default; ask only where the wrong pick changes an interface, a file or a promise.
4. **Record the pick as an ADR before the code.** `docs/adrs/NNN-<slug>.md` with `## Context`, `## Decision`, `## Consequences`. Read the directory **on the fetched remote head, not the working tree**, and the open pull requests, before choosing `NNN`: an ADR in review already owns its number, and a branch shows a shorter directory whose top number is taken on `main`. Take `max+1` from `git ls-tree --name-only origin/main docs/adrs/`, or from a throwaway clone. The Consequences say what the choice costs. The record stands alone: cite only lower-numbered ADRs, never `PRODUCT.md`, `SYSTEMS.md`, `DESIGN.md` or the README, which move with the version. The Context states the product premise in its own words; documents link to the record, never the reverse. **Check the batch's citations after drafting it, before the pull request.** A batch written in request order cites forward, and the fix is a renumber, not a rewritten sentence. No output from this loop means every record cites only lower numbers:

```bash
python3 - <<'PY'
import pathlib, re
for f in sorted(pathlib.Path("docs/adrs").glob("[0-9][0-9][0-9]-*.md")):
    n = int(f.name[:3])
    for c in re.findall(r"\]\((\d{3})-", f.read_text()):
        if int(c) >= n:
            print(f.name, "cites", c)
PY
```

5. **Sweep the documents the decision falsifies, in the same change.** A rule the product document still promises and the decision withdraws is deleted, not left beside its replacement; the system document's mechanism section, the design document's values — creating `DESIGN.md` when the repository carries none — the README's commands and the entry file's map follow. **An older ADR is immutable once merged: a contradicting decision is a new ADR naming the clauses it overrides.** `000` makes presence in `main` the status, so editing rewrites the history a reader relies on. The new ADR names the record and the clause ("this overrides `002`'s one-event bullet and its no-API consequence, and narrows `003`'s "never delayed" to one bounded read; everything else stands"); the falsified clause stays as what was believed then. A configuration list growing is the same act. An issue's _Done means_ naming an already-merged `NNN` gets a new ADR too, with the body saying why the named file was not edited.
6. **Land it by pull request**, one decision per PR, and report the link.

## The conflict pass

Read the edited documents against each other before opening the pull request. A decision can be right and still contradict the sentence beside it.

- **Never restate a closed set you are widening.** "One event acts: X" beside a document listing three is a contradiction; write "a third delivery acts" and let the mechanism list carry the set.
- **An override names only clauses that fell.** Claiming a clause that still governs tells the next reader a live rule is dead.
- **Scope a "no state" sentence to the addition.** "The assignment adds no state of its own" is true beside a per-pull-request count; "no state beyond the cache" denies it.
- **Retire the replaced vocabulary.** "The state does not call for it" assumes a board a service that "reads no board" cannot have.
- **A rule stated for one flow goes stale when a second arrives.** "A review request is never delayed" is false by omission beside an assignment that must be equally prompt; reread the run-start and failure paragraphs, not only the decision bullets.
- **A surface that becomes a mode re-decides every clause naming it.** Hiding a field changes the empty query, the cleared field, Esc, the text kept after a jump and the result set, each with a rule written for the always-visible surface. List every clause naming the surface before deciding the mode.
- **A mode that dims or hides the window keeps the failure surface readable.** A fade taking the status line to quarter strength keeps the pixel and loses the promise that a failed save is shown.
- **Grep the exact token your record quotes.** A record fixing an argv, flag or field name is a second copy of that string: a living document carrying `--source dispatch` against a record's `--source tool` ships two answers. Correct the living sentence, name it as found drift, and put the fallen value in the new ADR's override.
- **Cite a record for what it decided, never for a state of the tree.** A timing, a padding or a layout the record never fixed is described as what the code does now; an ADR number attached to it claims a clause that does not exist.
- **Count the records the sentence claims.** "One decision is recorded and not built" beside two ADR links is a contradiction; a version carrying several records counts them and links each.

## What the operator expects

- Options before any recommendation.
- **A brainstorm invitation is answered with a document.** Each option says what it buys, what it costs and what would kill it; the close is one first step carrying a number. The chat carries the verdict and the attachment, not the argument.
- Simplicity named as the priority unless they say otherwise; every option says what it rules out.
- Decisions arrive as numbered answers, each becoming a document rather than a paragraph of chat.
- **A design pull request's body names the judgement calls** — two or three forks the reviewer may want to reverse, each with its one-line consequence.
- **A prohibition the operator lifts moves the boundary; it does not remove it.** "It doesn't need to be read-only" instructs a new set, not a capability: name which writes, on what trigger, and which verbs stay refused by name (no label, no merge, no push, no review request, no dismissal). Record the platform's grant beside the act the code performs, because the grant is coarser — `issues: write` also closes and labels — and that gap is the reviewer's question.
- A scope cut ("ignore crash or restart") deletes the mechanisms that existed only for those cases; the design shrinks visibly rather than carrying a caveat.
- **A version's out-of-scope cases are a section, not a silence.** One heading, a lead sentence calling them deliberately unhandled, and one bullet per case naming the observable outcome — a wake that does not happen, a run that happens twice — never a plan to fix it. Probe what turns on another program's behaviour; only what a probe cannot reach is written "unrecorded here", with the workaround at the point of use.
- **An ADR records what is decided, not planned.** No "the next version will…", no roadmap in Context or Consequences; work left out is stated as cost. A cut feature is deleted, not left as a placeholder.
- **A configuration field earns its place by differing per host.** The webhook secret's name is configuration because each host names it; a fixed env-var name or port lives in code, with only its value in the host's env file.
- "Write only X" means exactly that: ripple fixes are the next pull request, named in the first body.
- A conflict pass is wanted after a docs change: separate the contradictions fixed here, the historical records left standing, and the files outside the pen.

## Planning ahead across versions

A "what should vN+1, vN+2 carry" request is not a decision to record: answer with the ranking, and write an ADR once the operator picks.

- **A version in review is not live.** Label the ranking as not decisions and record nothing; the pick is the operator's.
- **Ground in what was already deleted.** Search the restart's sessions for why the previous design failed: the largest-looking feature is usually the one withdrawn for weight. The `nuke!` commit's parent holds the deleted implementation — `git log --all --oneline -- <path>` names the files a reset dropped, `git show <nuke>^:<path>` reads one, `git grep -niE '<mechanism>' <nuke>^ -- 'docs/*.md'` finds the clause that priced it. Run this before answering, not after recommending.
- **Rank by the stated priority**, one line plus its single trade-off, then say which survive and which are out.
- **Re-read the fleet's workflow before ranking.** A change in review retires candidates: a wake for a human merge is worthless once approval is the merge. Cite such a skill by the pull request that carries it, re-rank in the next answer, and say which earlier recommendation the change killed.
- **Read the product's unhandled-cases section as the candidate list.** Each named gap is a version's work with its rationale and prior consent; anything else is a new surface and has to argue for itself.
- **One increment per version — one event or one behaviour.** An event plus a mechanism is two versions with one number, and the second is where state, credentials or a queue creep in. The exception is a version that adds no delivery but makes existing ones trustworthy, which says so plainly.
- **Rank by what fails silently, not by reach.** A wake started and never run, and a red default branch nobody is told about, cost more trust than a flow that does not exist. Spend those first and place the single widening last, so it can be dropped.
- **Weigh a candidate against the record.** `gh run list --repo <owner>/<repo> --branch main --limit 100 --json conclusion,event,name` counts the failures a version would have acted on, `gh pr list --state merged` sizes the period, and `session_search` shows a pull request woken three times in eight minutes. A case that occurred is a demonstrated gap; none is insurance. A code-scanning run reports `dynamic`, not `push`, so it is not a red `main`.
- **Name what is out and the invariant it costs** ("never hold a wake back", "no durable state", "calls no API"), not just that it is deferred.
- **Close with what would change the recommendation.**
- **Read the event's payload schema before promising who is woken.** A target the payload lacks is out before it reaches the list: `workflow_run` names pull requests by number and refs, not author, so "a failing check wakes the author" is unimplementable without the API read the service forbids. The schema is plain JSON at `raw.githubusercontent.com/octokit/webhooks/main/payload-schemas/api.github.com/<event>/<action>.schema.json`, with object fields under `common/<object>.schema.json`. Read the **action's** schema: `issues`/`unassigned` makes `assignee` optional where `pull_request`/`unassigned` requires it, and a dismissed review carries `simple-pull-request`, whose merge fact is `merged_at`. A field the schema does not require pairs with "wakes nobody when it is absent".
- **Read a platform capability's availability contract at ranking time.** The generated declarations (`types/tiny.d.ts`, `types/tjs.d.ts`) are the API the app compiles against. A capability on one OS (`tiny.macos.ai`: macOS 26+, Apple Intelligence on, `unsupported` elsewhere) is a platform split that ranks last unless the operator wants one. A runtime caveat (`tiny.hotkey` never fires on Wayland without the GlobalShortcuts portal) belongs in the product sentence. Check a SQL feature against the runtime's build flags (FTS5 in the vendored SQLite), not SQLite's manual.
- **A roadmap is decided, not scheduled.** One delivery added per version, no new mechanism, a record per version before its code. Once the operator says record it: PRODUCT carries a _Changelog_ (one line per shipped version, the deleted predecessor left out) and a _Roadmap_ (one line per decided version linking its ADR, led by a sentence saying it is not built); each decided version gets its own ADR now, about what, never when; SYSTEMS carries the mechanisms in _Planned, not built_, not in the present-tense lists. Present-tense acceptance a decided version retires is named in the ADR's override as falling when the code lands.
- **Number the roadmap from the releases, not the document.** Read `gh release list --repo <owner>/<repo>`, the tags and the version file on `main` before writing "v1.2": a release can land while the plan is still in chat. A binary ahead of its record is repaired in the same pull request.
- **Shape the documents from the previous version's docs-ahead pull request.** `gh pr view <n> --json commits`, `git fetch origin pull/<n>/head:pr<n>`, then `git show pr<n>:docs/PRODUCT.md` — copy the shape, replace the decision. When none exists, `git log --all --oneline -- PRODUCT.md` finds a commit that carried it.
- **A new product's first product document may carry a candidate list.** A `Roadmap` led by _Candidates, not commitments_: one line per version, no ADR, only the version being specified decided.

- **A plan for an unbuilt surface keeps the product document describing the binary.** The roadmap line says decided and not built. The system document's _Planned, not built_ section names the mechanisms. The new interface goes in its own file under `docs/`, linked from that section. `PRODUCT.md`'s present-tense rules and acceptance stay true until the surface ships. A spec that widens the product document early puts an acceptance list on a binary that cannot meet it.
- **A repository with no roadmap carries the plan in the system document alone.** The records land In Review, _Planned, not built_ states the mechanism in about four sentences and links each record, and its lead sentence counts them ("two things are decided and unbuilt"). The paragraph summarises the records; it never restates a rule one owns, and the product document keeps describing the shipped binary until the change lands.

## Sizing a decided-but-unbuilt change

"How complex is it to add X" is a read of the tree, not of the record: the ADR says what was chosen, the code says which seams it must cross.

- **Read the ADR, then list touch points in the tree.** `ls internal/`, the handler's decision function, `main`'s listeners; a new package plus one call site plus one wiring block is the small case. An estimate from prose misses the plumbing every route needs: a listener that fails at boot, a shutdown path, a golden-output test.
- **Put a number on each axis before calling it small or medium.** Count the call sites the change rewires (`grep -o 'entry\.text' | wc -l`), the file's lines, the tests that must stay green, the bytes the artifact grows by, and the versions the product has shipped — a stated figure is reviewable and an adjective is not.
- **A closed enumeration in an older ADR is stale once a later ADR adds a state.** Read the ADR directory in number order, diff the sets, and settle the seam with a short new ADR naming the clause it overrides.
- **Instrumentation must sit on a path the code runs.** A follow-up run started from the exit path has no delivery, event or duration: read that path (`exit`, `followUp`) before promising one instrument covers both.
- **A label drawn from a request header is unbounded until you find the guard.** `X-GitHub-Event` is attacker-controlled; cardinality is bounded only because an unsigned delivery returns before a label is recorded, and every value still needs escaping.
- **Separate decided from unbuilt from out of scope.** An unimplemented ADR is work; the _What it never does_ and edge-case lists are deliberate refusals and must not be counted in the estimate.
- **A change that adds interpretation to stored text has a migration even when no row moves.** Old notes start rendering without an edit: name the marker pairs that would fire, the part of the log they touch, and the subset rule that keeps the surprise small (one delimiter family, no `_`). A schema diff shows nothing, so this is the compatibility cost a reader finds the hard way — and the one an impact note must lead with.

## Probing a behaviour a decision turns on

A claim about another program — GitHub, Hermes — is sourced or observed, never guessed. When it decides a branch, a wake or a product sentence, observe it before writing the record; "unrecorded here" is reserved for what a probe cannot reach.

- **Read another program at the version the host runs, not `main`.** `raw.githubusercontent.com/<owner>/<repo>/<tag>/<path>` answers a flag, default or validation rule. Take the version from the repository's record — a boot line, an incident body, the operator — and cite the tag: "this flag exists" is true of one release and false of another.
- **A runtime capability is settled by running the runtime.** Drive the binary the app ships from a throwaway script — `~/.tinyjs/bin/tjs run probe.js` opening `tjs:sqlite`: create the structure, exercise the triggers through insert, update and delete, confirm the tokenizer's folding (`remove_diacritics 0` keeps å, ä and ö distinct), and measure what the record will claim.
- **GitHub webhook deliveries, end to end.** Create a hook on a repository you administer with an unreachable URL — `gh api -X POST repos/<owner>/<repo>/hooks -f name=probe -F active=true -f 'events[]=issues' -f 'events[]=pull_request' -f 'config[url]=https://example.invalid/probe' -f 'config[content_type]=json' -f 'config[secret]=<throwaway>'` — perform the gesture through `gh`, then read `gh api repos/<owner>/<repo>/hooks/<id>/deliveries --jq '.[] | [.id,.event,.action,.status] | @tsv'`. A delivery that cannot connect is still recorded, so nothing has to listen; sort by `id` for the true order.
- **Do the gesture the question is about**, not a paraphrase: an issue created with an assignee, a pull request created with an assignee, a draft marked ready. One hook subscribing to every event involved answers three questions in one pass.
- **Clean up and cite.** Delete the hook (`gh api -X DELETE …/hooks/<id>`), close the probe issues and pull requests, and put the observation and its date in the record.
- **A probe that closes a case shrinks the design.** Delete the branch and the product's edge bullet rather than keeping a code path for a doubt that no longer exists.
- **A dependency's cost is measured, not estimated.** Build the claim in a scratch module under `/tmp`: `go get` the package, compile a program using it, and diff the binary against a baseline that imports what the real binary already imports. Report the bytes, the `go.sum` line count and the direct requires.
- **A browser dependency is priced from its tarball.** `curl -fsSL $(npm view <pkg> dist.tarball) | tar xz`, then `gzip -c9 <file> | wc -c` for the bytes the page fetches. Count the wasm and each wrapper separately — a SQLite build is 406 KB gzipped for the wasm and about 190 KB more for a JavaScript wrapper and the OPFS proxy — and quote the sum, because that is what the first load carries.
- **Price the layer, then ask whether the signal earns it.** In the Go OpenTelemetry SDK the API is small and the OTLP exporter is nearly all the rest, because it drags gRPC, protobuf and `genproto` in. Measure the variant the service would run, not the smallest import that compiles. With no inbound trace context and no instrumented child, a span is a root with one attribute set and a duration — a log line with timing — while the operator's questions (how many, how often, how slow, did it fail) are a counter and a histogram. A standard-library metrics endpoint in Prometheus text on a fixed loopback port, scraped by a stock collector (Grafana Alloy or `otelcol`), keeps the module clean and the provider choice in the collector.

## Containerising a service that drives the host

A container has its own PID and filesystem namespace: it cannot start the host's process or write the host's store. Decide by what the process touches.

- **Touches no host state** — an exporter, a collector, a proxy — containerise it. It also gains: a third-party binary with its own cadence and no host integration.
- **Spawns the host's binary or writes the host's store** — it stays on the host, or takes one of three shapes: everything in one image (store, credentials and repos mounted, the runtime socket passed through — a chroot that hands the image control of the host's containers); a host-side broker (a socket-activated unit that takes the verb and execs it — least privilege, but a second component and a second contract); or the runtime's own API (no mounts or socket, but the daemon becomes a hard dependency of every action, and what the spawned process reported back becomes the daemon's record).
- **Check the runtime's API before assuming the third shape must be built.** Hermes' gateway webhook platform runs a named profile when `gateway.multiplex_profiles` is on, with a route bound to the profile and its own HMAC secret (`hermes-agent`, `references/webhooks.md`) — "wake profile X" is already an HTTP verb.

Name the invariant each shape costs before recommending one, and keep the container as the question rather than the goal.

## Pitfalls

- **A wake cannot steer a run in flight, so no candidate may mean "stop".** A wake starts a new child whose whole input is the reason; the running session has no inbox, so an "unassigned" or "cancelled" wake starts a further session that knows nothing of it. Test every candidate against "the agent re-reads and decides": a state change only an in-flight run could act on is a process problem, not a version. A session is nameable and resumable, a process has a pid, and only a gateway chat session has an inbox a message reaches.
- **"A duplicate is harmless" is a claim about the agent's answer, not about concurrency.** Name the artifact the run publishes: one that posts a review or comment cannot repeat, because two live runs read the same head and neither merges with an answer it cannot see.
- **A rule in the agent's skill cannot close a race between runs.** "Check for your own earlier review" is check-then-act against a surface another run writes, and the window is a whole run. Fix it in the service that starts runs — one in-flight key per object and profile, one held follow-up started on exit.
- **A serialisation structure holds the smallest thing that answers the concurrency, keyed by every party that may act in parallel.** A wake is a reason, not an instruction: when the consumer re-reads state at start, N held wakes for one subject are one read, so one slot with replacement loses nothing and a FIFO queue costs N runs of latency. Key by subject _and_ actor, or a reviewer's run holds the author's wake and the loop becomes a cycle. A run table earns its place only when a version bounds or kills a run, since it owes a lifetime bound, a kill path and a boot reconcile.
- **A withdrawn candidate is recorded in the pull request body, not an ADR.** An ADR records what survives into the code; a candidate killed on mechanism grounds has no clause to override, and a record for it turns the directory into a diary. Name the code and line that make it impossible.
- **When a second record would widen the same clause again, close the family.** The newer record restates the rule's shape once — the kinds of line it now has — and says a further kind needs its own reason.
- **A flow that needs a new surface is two records, and the surface is written first.** A page or panel a flow starts from has its own navigation, close and lifetime, and can outlive the flow. Numbers only go backwards, so let the flow record decide only format, destination and failure path.
- **Composing an ADR from a sibling repository's precedent means re-checking every relative link.** A restarted repository keeps the old numbers but not its files, so a copied `009-…` link points at nothing. Number from the target directory, and resolve every `](…)` relative to the file's own directory — a link copied from another depth (`../001-…`) points above the repository.
- **An ADR's override names the clause, not the vibe.** "This overrides 002" leaves a reader guessing; quote the bullet's own words ("one event acts") and say which parts still stand.
- **A mechanism's failure mode is part of its cost.** One that depends on a daemon nothing guarantees fails silently, which is worse than a heavier mechanism that fails loudly.
- **A decision written ahead of the code is a promise the first implementation must not contradict.** The change that contradicts the record is the one that changes.
- **Name the unit a loop cap counts, and gate every wake that advances the loop.** A cap on "reviews" is ambiguous between the request that wakes the reviewer and the changes-requested review that wakes the author: pick one as the round and apply the cap at both wakes. Check before incrementing so the tenth acts and the eleventh is refused, and state the count's lifetime in one clause.
- **Test the actor rule against the case the event exists for, and write the exception it needs.** "The delivery's own actor is never woken" silences exactly the self-caused cases: the author's push fails the checks, and the author's rebase dismisses the stale approval. Where it must fall, name the record that fell the same way (`010`) and say which half still holds — the override is per event, never global.
- **A version bump is a stale fact in more places than the behaviour sentence.** The product document's version line and its "vX is done when" acceptance, the system document's mechanism, storage, failure, check and _Planned, not built_ lists, and the README's one-line description each carry the old version or the old absence ("no cap"); grep both after editing. In a design-only pass the README is left alone — it describes the running binary. The entry file's _Current Project Focus_ is the operator's, named in the body. Older ADRs naming the previous version are immutable: name them in the new record's override.
- **A cap that resets by clearing its counter is only true if nothing else advances the counter.** If it keeps incrementing while the stop signal is present, the budget is spent before the operator acts. State both halves, and check the increment site against the guard's read site.
- **An acceptance item that asks a new question needs a field in the record that answers it.** Adding "whether the label was written" to acceptance without adding it to the audit line's field list makes the record's "answers the acceptance exactly" false. First check whether a field it carries can answer — a free-text decision can hold the label outcome, an enumerated list needs an override ADR. Give a failed write its own decision value.
