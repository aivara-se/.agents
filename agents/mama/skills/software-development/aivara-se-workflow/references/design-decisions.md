# Designing and recording a decision

## The loop

1. **Ground before proposing.** Fetch the repository, read the product and system documents and every ADR in `docs/adrs/`, the fleet's shared skills in `aivara-se/.agents` and any open pull request against them, and search past sessions for earlier attempts (`session_search`). The workflow the product serves lives in those skills, and a change in review there can retire a candidate before it is proposed. Name what was tried and why it failed; a mechanism proposed from memory repeats a decision the repository already withdrew.
2. **Answer with options first.** A numbered list, each option one line plus its single trade-off, ordered by the stated priority. Then say which survive that priority and why the others are out — the operator reads the list before the recommendation.
3. **Recommend one and take the defaults.** Every fork that does not change the artifact gets a default, named in the answer; ask only the forks where the wrong pick changes an interface, a file or a promise.
4. **Record the pick as an ADR before the code.** `docs/adrs/NNN-<slug>.md` with `## Context`, `## Decision`, `## Consequences`. Read the directory **on the fetched remote head, not the working tree**, and the open pull requests, before choosing `NNN` — an ADR in review already owns its number, and a tree sitting on another branch shows a shorter directory whose highest number is already taken on `main`. Take `max+1` from `git ls-tree --name-only origin/main docs/adrs/`, or from a throwaway clone of the remote, before writing the file. The Consequences say what the choice costs, not only what it buys. The record stands alone: cite only ADRs with a lower number, and never `PRODUCT.md`, `SYSTEMS.md`, `DESIGN.md` or the README — those move with the version, and a link to one rots. The Context states the product premise the decision needs in its own words; the documents may link to the record, never the reverse.
5. **Sweep the documents the decision falsifies, in the same change.** A rule the product document still promises and the decision withdraws is deleted, not left beside its replacement; the system document's mechanism section, the README's commands and the entry file's map follow. **An older ADR is immutable once it has merged: a decision that contradicts one is a new ADR that names the clauses it overrides.** Do not edit the merged record — `000` makes presence in `main` the status, so editing it rewrites the history a reader relies on, and an in-place amendment made before this rule is not precedent to copy. The new ADR carries the override in its Context, naming the record and the bullet or consequence ("this overrides `002`'s one-event bullet and its no-API consequence, and narrows `003`'s "never delayed" to one bounded read; everything else stands"), and the falsified clause is left as the record of what was believed then. Say what still holds, not only what changed: a reader arriving at the old record needs to know which half of it their decision depends on. A configuration list growing is the same act — a new ADR that names the list it extends. An issue's *Done means* that says "the chosen rule is in `NNN`" where `NNN` has already merged is answered the same way: a new ADR that names the clauses it overrides, and a sentence in the pull request body saying why the named file was not edited, so the reviewer does not read the untouched record as a skipped acceptance item.
6. **Land it by pull request**, one decision per PR, and report the link.

## The conflict pass, after the ADR is written

Read the edited documents against each other before opening the pull request. A decision can be right on its own and still contradict the sentence beside it, and the reviewer finds that first.

- **Never restate a closed set you are widening.** A new bullet reading "one event acts: X" while the system document lists three is a contradiction; write the addition ("a third delivery acts") and let the one mechanism list carry the set.
- **An override section names only clauses that actually fell.** Claiming an earlier record's clause that still governs its own flow ("nothing else changes") tells the next reader a live rule is dead; the surviving half is what the implementation still obeys.
- **Scope a "no state" or "nothing else changes" sentence to the addition.** "The assignment adds no state of its own" is true beside an existing per-pull-request count; "no state beyond the cache" reads as a denial of the count the storage section lists.
- **Retire the vocabulary of the architecture the decision replaces.** "The state does not call for it" assumes a board that a service which "reads no board" cannot have; a sentence carried over from the previous version carries its premise with it.
- **A requirement stated for one flow goes stale when a second arrives.** "A review request is never delayed" is false by omission beside an assignment that must be equally prompt; reread the run-start and failure paragraphs, not only the decision bullets.
- **Grep the exact token your record quotes, not just the version number.** A record that fixes an argv, a flag or a field name is a second copy of that string, so a living document still carrying the old value (`--source dispatch` against a record's `--source tool`) ships two answers in one change and the reviewer finds the contradiction first. Correct the living sentence, name it in the body as found drift, and put the immutable record's fallen value in the new ADR's override section — never edit the merged ADR.

## What the operator expects

- Options before any recommendation.
- Simplicity named as the priority unless they say otherwise; every option says what it rules out.
- Decisions arrive as numbered answers, and each one becomes a document rather than a paragraph of chat.
- A scope cut ("ignore crash or restart") deletes the mechanisms that existed only for those cases; the design should shrink visibly rather than carry a caveat.
- **A version's out-of-scope cases are a section, not a silence.** When the operator asks for edge cases and says they are not handled, the product document gets its own heading that says so, a lead sentence calling them deliberately unhandled in this version, and one bullet per case naming the observable outcome — a wake that does not happen or a run that happens twice — never a plan to fix it. Where a case turns on another program's behaviour, probe it before writing the bullet (*Probing a behaviour a decision turns on*): an observable answer either closes the case or shrinks the decision, and only what a probe cannot reach is written "unrecorded here", with the workaround at the point of use. Asserting the behaviour to make the bullet read cleaner puts a guess in the record, where the next reader treats it as fact.
- **An ADR records what is decided, not what is planned.** No "the next version will…", no "the cap is a later decision", no roadmap in Context or Consequences — a reader at the record is asking what is true now. Work left out is stated as cost (what the choice does not do, and what that costs today), never as a promise of when it will be picked up. The same applies when a feature is cut on request: delete it from the documents rather than leaving a placeholder for it.
- **A configuration field earns its place by differing per host, not by symmetry with a neighbour.** The webhook secret's name is configuration because each host names it; that does not make a second secret's name a field. A fixed environment-variable name is the service's and lives in code, with only its value in the host's env file — a field that merely restates it is validation the loader carries for no gain, and a fixed port is the same kind of value — it belongs in the code, with the scraper's target or the client's URL naming it.
- "Write only X" means exactly that: the ripple fixes are the next pull request, named in the first body.
- A conflict pass is wanted after a docs change, not only a sweep for the old wording: the operator asks whether the documents disagree with each other or with the decision, and the answer separates the contradictions fixed in the change from the historical records left standing on purpose and the files outside the pen (the entry file, the code).

## Planning ahead across versions

A "what should vN+1, vN+2, vN+3 carry" request is not a decision to record: answer with the ranking, and write an ADR only once the operator picks one.

- **Ground in what was already deleted.** Search the restart's sessions for why the previous design failed before naming candidates; the largest-looking feature is usually the one withdrawn for weight, and re-proposing it repeats a decision the operator already paid for. The `nuke!` commit's parent still holds the deleted implementation, and the tree answers faster than the sessions: `git log --all --oneline -- <path>` names the files a reset dropped, `git show <nuke>^:<path>` reads one, and `git grep -niE '<mechanism>' <nuke>^ -- 'docs/*.md'` finds the clause that priced it — which says what the mechanism cost, not only that it was tried. A mechanism the operator proposes while asking "would this be simpler" is often exactly the deleted one, so run this before answering rather than after recommending.
- **Rank candidates by the stated priority, each one line plus its single trade-off**, then say which survive and which are out. The operator reads the list before the recommendation.
- **Re-read the fleet's workflow before ranking, because a change in review retires candidates.** The `.agents` skills say what wakes an agent and how a change lands; when one is being rewritten, a candidate built on a step that is disappearing is already dead — a wake for a human merge is worthless once the approval is the merge, and a draft's ready transition only matters once drafts are the do-not-arm lane. Cite such a skill by the pull request that carries it, re-rank in the next answer, and say plainly which earlier recommendation the change killed rather than quietly replacing it.
- **Read the product's unhandled-cases section as the candidate list before inventing one.** Every gap the document already names as deliberately unhandled is a version's worth of work with its rationale attached and the operator's prior consent on record; a candidate that is not in that list, or in the *What it never does* list read backwards, is a new surface and has to argue for itself.
- **One increment per version — one event or one behaviour.** A version that adds an event *and* a mechanism is two versions with one number, and the second is where the state, credential or queue creeps in. The exception is a version that adds no delivery because it makes the existing ones trustworthy — the run's exit status in the audit, a failure nobody was told about — which is narrower than a delivery and says plainly that it breaks the one-delivery rhythm.
- **When the loop is already sufficient, rank by what fails silently, not by reach.** A wake that is started and never runs, and a red default branch nobody is told about, cost more trust than a flow that does not exist yet: the operator cannot see the first two at all, and re-reads the log precisely because a wake was missed. Spend the trust versions first and place the single widening last, so it can be dropped if the first two show the fleet is fine; say that ordering rule out loud, because it is the part of the answer the operator is judging.
- **Weigh a candidate against the repository's own record before ranking it, and read the field that makes the record evidence.** `gh run list --repo <owner>/<repo> --branch main --limit 100 --json conclusion,event,name` counts the failures a version would have acted on, `gh pr list --state merged` sizes the period, and `session_search` shows a pull request woken three times in eight minutes. A candidate whose case has occurred is a demonstrated gap; one with no occurrence is insurance; say which is which instead of asserting urgency. Read `event` before citing a red `main`: a code-scanning run reports `dynamic`, not `push`, so a formatter or CodeQL failure is not evidence for a flow keyed on the push event — citing it makes the record's own ground false.
- **Name what is out and the invariant it would cost** ("never hold a wake back", "no durable state", "calls no API"), not just that it is deferred. That sentence is the useful part; the deferral list is not.
- **Close with what would change the recommendation** — a priority the operator has not stated, such as cost over latency — rather than hedging.
- **Before a version promises who is woken, read the event's payload schema — at ranking time, not when the sentence is written.** A candidate whose target the payload does not carry is out before it reaches the list, and one whose field is there (the run's `actor` and `head_branch`, a review's `body` and `author_association`, an inline comment's own) needs no API read to become a version. The target a product sentence names must be a field the delivery actually carries: `workflow_run` names its pull requests by number and refs, not by author, so "a failing check wakes the author" is unimplementable without the API read the service forbids. Read the schema and let it decide the sentence: the octokit copy is plain JSON at `raw.githubusercontent.com/octokit/webhooks/main/payload-schemas/api.github.com/<event>/<action>.schema.json`, with each object's own fields under `common/<object>.schema.json`, and it carries the array item shapes the prose page omits. Read the **action's** schema, not the event's: required-ness differs per action — `issues`/`unassigned` makes `assignee` optional where `pull_request`/`unassigned` requires it, and a dismissed review carries the pull request as `simple-pull-request`, whose merge fact is `merged_at` rather than a boolean. A field the schema does not require is a field the sentence must pair with "wakes nobody when it is absent". Then write the proxy and its cost into the record rather than asserting the convenient target. A roadmap approved in chat is reshaped by this finding, not exempted from it.

- **A roadmap is decided, not scheduled, and the operator's default is simplicity plus demonstrated value**: one delivery added to the set the service acts on per version, no new mechanism, and a record per version before its code. The plan stays a conversation until the operator says to record it; once they do, three things land together and none of them is a date. PRODUCT carries a *Changelog* — one line per shipped version, the deleted predecessor left out — and a *Roadmap*, one line per decided version linking its ADR and led by a sentence saying it is not built. Each decided version gets its own ADR now: a decision about what the version does, never when. SYSTEMS carries the mechanisms in its own *Planned, not built* section rather than widening the present-tense lists — the delivery list, the fixed reason sentences and the subscription sentence still describe the running version, and a lead line says so. A mechanism the roadmap adds (a counter, an actor-rule exception) is named there and nowhere else. The present-tense halves stay true: PRODUCT's edge bullets and acceptance lines that a decided version retires are named in the ADR's override section as falling when the code lands, never deleted while the binary still behaves the old way — a document whose acceptance describes a version the binary does not run is the same lie as a map that names a path the tree has dropped.

- **Shape the decided version's documents from the previous version's docs-ahead pull request.** The last version that landed this way still carries its pre-code state in git: `gh pr view <n> --json commits`, `git fetch origin pull/<n>/head:pr<n>`, then `git show pr<n>:docs/PRODUCT.md` and `docs/SYSTEMS.md` read the Roadmap section, its lead sentence and the *Planned, not built* paragraph exactly as this repository writes them — copy the shape and replace the decision. More faithful and cheaper than re-deriving the format from the shipped tree, where the roadmap line has been consumed by the changelog entry and the Planned paragraph deleted.

- **A new product's first product document may carry a candidate list, and that is not yet a roadmap.** When the operator asks for the version arc at the project's birth, a `Roadmap` led by *Candidates, not commitments* is allowed: one line per version, no ADR, and only the version being specified is decided. It ranks direction, not schedule; each later line becomes a roadmap entry with its ADR when the operator picks it.

## Probing a behaviour a decision turns on

A claim about another program — GitHub, Hermes — is sourced or observed, never guessed. When the answer decides a branch, a wake or a product sentence, observe it before writing the record; "unrecorded here" is reserved for what a probe cannot reach.

- **Read another program at the version the host runs, not at `main`.** A flag, a default or a validation rule is a property of a release: `raw.githubusercontent.com/<owner>/<repo>/<tag>/<path>` answers it, and `main` may be an upgrade ahead or a release behind. Take the version from the repository's own record — a boot line, an incident body, the operator — never from a guess, and cite the tag beside the observation, because "this flag exists" is true of one release and false of another. Where the two disagree the tag decides what to build; `main` only says where the project is going.

- **GitHub webhook deliveries, end to end.** Create a hook on a repository you administer with an unreachable URL — `gh api -X POST repos/<owner>/<repo>/hooks -f name=probe -F active=true -f 'events[]=issues' -f 'events[]=pull_request' -f 'config[url]=https://example.invalid/probe' -f 'config[content_type]=json' -f 'config[secret]=<throwaway>'` — perform the gesture through `gh`, then read `gh api repos/<owner>/<repo>/hooks/<id>/deliveries --jq '.[] | [.id,.event,.action,.status] | @tsv'`. A delivery that cannot connect is still recorded, so nothing has to listen; sort by `id` for the true order.
- **Do the gesture the question is about**, not a paraphrase of it: an issue created with an assignee, a pull request created with an assignee, a draft marked ready. One hook subscribing to every event involved can answer three questions in one pass.
- **Clean up and cite.** Delete the hook (`gh api -X DELETE …/hooks/<id>`), close the probe issues and pull requests, and put the observation and its date in the record — "observed 2026-10-20" is a source under the reason rule, and saying the probes were removed is part of the report.
- **A probe that closes a case shrinks the design.** When it shows the case is already handled, delete the branch and the product's edge bullet instead of keeping a code path for a doubt that no longer exists; that is the cheapest scope cut available, and it usually makes the version simpler than the plan approved in chat.
- **A dependency's cost is measured, not estimated.** Before an ADR admits the repository's first third-party module, build the claim in a scratch module under `/tmp`: `go get` the package, compile a program that uses it, and diff the binary against a baseline that imports what the real binary already imports — a bare `println` baseline counts the standard library the service already links and overstates the delta. Report the bytes, the `go.sum` line count and the direct requires in the record; that number is what makes the Consequences honest, and it is what the operator reads before accepting a tree they now maintain.
- **Price the layer, then ask whether the signal earns it.** A dependency's cost is rarely uniform: in the Go OpenTelemetry SDK the API is a couple of megabytes and the OTLP exporter is nearly all the rest, because it drags gRPC, protobuf and `genproto` in. Measure the variant the service would actually run — every SDK, every exporter — not the smallest import that compiles, and name the heavy layer in the record. Then check what consumes the signal: with no inbound trace context and no instrumented child, a span is a root carrying one attributes set and a duration, which is a log line with timing, while the operator's questions (how many, how often, how slow, did it fail) are a counter and a histogram. Moving the OTel boundary out of the binary — a standard-library metrics endpoint in Prometheus text on a fixed loopback port, scraped by a stock collector that exports OTLP — keeps the module clean, keeps the provider choice in the collector's configuration, and stays reusable by every service on the host in a way a tailored sidecar does not.

## Containerising a service that drives the host

A container has its own PID and filesystem namespace: it cannot start the host's process or write the host's store by itself. Decide by what the process touches, not by what a container would make convenient.

- **Touches no host state** — an exporter, a collector, a proxy — containerise it. It is also the piece that gains: a third-party binary with its own upgrade cadence and no host integration.
- **Spawns the host's binary or writes the host's store** — it stays on the host, or it takes one of exactly three shapes, each with a named cost: everything in one image (the store, credentials and repos mounted, the container runtime's socket passed through — a chroot that hands the image control of the host's containers); a host-side broker (a socket-activated unit that takes the verb and execs it — least privilege, but a second component and a second contract); or the runtime's own API, when one exists (no mounts and no socket, but the runtime daemon becomes a hard dependency of every action, and whatever the spawned process reported back — exit status, source tag — becomes the daemon's record instead).
- **Check the runtime's API before assuming the third shape must be built.** Hermes' gateway webhook platform can run a named profile when `gateway.multiplex_profiles` is on, with a route bound to the profile and its own HMAC secret (`hermes-agent`, `references/webhooks.md`) — "wake profile X" is already an HTTP verb, which is the whole of what a spawner does.

Name the invariant each shape costs before recommending one, and keep the container as the question rather than the goal: a service whose only job is to call the host's runtime is the process that containerising cannot improve.

## Pitfalls

- **A wake cannot steer a run in flight, so no candidate may mean "stop".** A wake starts a new child whose whole input is the reason; the run already working has no inbox a later delivery can reach, so an "unassigned" or "cancelled" wake starts a further session that knows nothing about the one still running. Making one reach takes a run table keyed by profile and object plus a signal — the tracking the run record refuses — and the duplicate runs that record allows leave "which one" undefined. Test every candidate against "the agent re-reads and decides": a state change only an in-flight run could act on is a process problem, not a version. Separate the three planes such a question can land on — a session is nameable, listable and resumable; a process has a pid and can be killed; only a gateway chat session has an inbox a message reaches — and answer from the plane the run mechanism actually provides, so the verdict is checkable rather than dogmatic. When the operator proposes one, confirm it against the run-start code and say which mechanism it would need before withdrawing it.
- **"A duplicate is harmless" is a claim about the agent's answer, not about concurrency: name the artifact the run publishes.** A wake whose answer is a re-read can be repeated; a wake whose answer is a posted artifact — a review, a verdict, a comment — cannot, because two live runs over one object each read the same head and each publish part of it, and neither can merge with an answer it cannot see. Before keeping a no-serialisation trade, say what the run writes and whether a second copy merges or collides; where it collides the trade buys latency with correctness, and the record has to say so rather than calling the repeat harmless.
- **A rule in the agent's skill cannot close a race between two runs; the serialisation belongs where the concurrency is.** "Check for your own earlier review on this head before submitting" is check-then-act against a surface another run writes, and the other run may publish between the check and the act — the window is the whole duration of a run, not a scheduling gap. Fix it in the service that starts the runs (one in-flight key per object and profile, one held follow-up started on exit) and keep it out of the profile's skill, because a rule that is only correct when every profile obeys it is broken by the first one that does not.
- **A serialisation structure holds the smallest thing that answers the concurrency, and its key names every party that may act in parallel.** A wake is a reason, not an instruction: when the consumer re-reads authoritative state at start, N held wakes for one subject are one read, so one slot with replacement loses nothing and a FIFO queue starts N runs to answer one at N runtimes of latency — the record says why replacement is safe, never merely that it is. Key by subject *and* actor: a subject-only key lets a reviewer's run hold the author's wake and the author's hold the reviewer's, which turns a loop into a cycle rather than a queue. A run table earns its place only when the version bounds or kills a run, and it belongs with that version, because a table owes a lifetime bound, a kill path and a boot reconcile — the three mechanisms a restarted repository stopped maintaining. Where the heavier structure has already been withdrawn, the record says what the value is *not* ("the value is the held delivery; nothing describes a live child"), because the same map under the same name reads as the table and the next session re-proposes it.
- **A withdrawn candidate is recorded in the pull request body, not in an ADR.** An ADR records what survives into the code; a candidate killed on a mechanism ground has no clause to override and nothing for a reader to obey, and a record for it turns the directory into a diary. Name the code and line that make it impossible, so the next session does not re-propose it, and keep the ADR numbers for what stands.
- **When a second record would widen the same clause again, close the family instead.** Two ADRs in a row overriding one rule ("one line per delivery") read as accretion; the newer record restates the rule's shape once — the kinds of line it now has — and says a further kind would need its own reason. Say it in the newer record; the older one stays as it was believed then.
- **Compose an ADR from a sibling repository's precedent, then re-check every relative link against the tree it lands in.** A restarted repository keeps the old one's ADR numbers and vocabulary but not its files: a link copied from the predecessor (`009-…`) points at nothing, and the reviewer fails it. Number the next ADR from the target directory after reading it, and resolve every `](…)` against the tree before the commit — relative to the file's own directory, so a link copied from a file at another depth (`../001-…` from a nested file) points above the repository and needs the extra level dropped, and a checker that prefixes a base onto a path that already carries one reports breaks that are not there.
- **An ADR's override section names the clause, not the vibe.** "This overrides 002" leaves a reader guessing which sentence fell; quote the bullet's own words (`"one event acts"`, "the service calls no API") and say which parts still stand, because the old record is left untouched as the account of what was believed then.
- A mechanism's failure mode is part of its cost. One that depends on a daemon nothing guarantees fails silently, which is worse than a heavier mechanism that fails loudly — say so while the option is on the table.
- A decision written ahead of the code is a promise the first implementation must not contradict; the ADR and the code land in that order, and the change that contradicts the record is the one that changes.
- **Name the unit a loop cap counts, and gate every wake that advances the loop.** A cap on "reviews" is ambiguous between the review request that wakes the reviewer and the changes-requested review that wakes the author; pick one as the round, say which reviews count and which do not, and apply the cap at both wakes, because suppressing only one leaves the other to continue the loop. Check the cap before incrementing so the tenth round acts and the eleventh is refused, and state the count's lifetime in one clause — process lifetime when restarts are out of scope — rather than designing expiry or a reset nobody asked for.
- **Test the actor rule against the case the event exists for, and write the exception the event needs.** Every event inherits "the delivery's own actor is never woken", and the service's two self-caused cases are exactly the ones a rule keeps silent: the author's own push is what fails the checks, and the author's own rebase is what dismisses the stale approval. A record that keeps the rule for such an event wakes nobody for its own premise. Read who performs the gesture in the case the operator described before writing the clause, and where the rule must fall, name the record that already fell the same way (`010`) and say which half of it still holds — the override is per event, never global.
- **A version bump is a stale fact in more places than the behaviour sentence.** The product document's opening version line and its "vX is done when" acceptance, the system document's mechanism, storage, failure, check and *Planned, not built* lists (which still call the shipped version unbuilt), and the README's one-line description each carry the old version or the old absence ("no cap"); after editing, grep the old version number and the withdrawn words across the repository. In a design-only pass the README is the one document left alone: it describes the binary that is actually running, so it keeps the old version and the pull request body says it lands with the code. The entry file's *Current Project Focus* is the operator's and is named in the pull request body, not edited — until the operator asks for it, which is the turn to edit it on the same branch, re-run the link and gate checks, and correct a body that said the file was theirs. The older ADRs' Context lines that name the previous version ("the one flow v1 carries") are immutable too — name them in the new record's override section instead of editing them, and read the whole ADR directory before assuming a clause is still true.
- **A cap that resets by clearing its counter is only true if nothing else advances the counter.** A loop cap that writes a durable stop signal and clears its count promises a fresh budget when the signal is removed; if the count keeps incrementing on deliveries that arrive while the signal is on, the budget is spent before the operator acts and the first delivery after removal re-blocks. State both halves — the counter does not advance while the signal is present, and it clears when the write succeeds — and check the increment site against the guard's read site, because a first draft usually counts before it checks.
- **An acceptance item that asks a new question needs a field in the record that answers it.** Adding "whether the label was written" to a product's acceptance without adding it to the audit line's field list leaves the promise unanswerable and makes that record's own "answers the acceptance exactly" false. Sweep the ADR that owns the record in the same change — and because that record is immutable, that is a new ADR that overrides its field list and its "answers the acceptance exactly" consequence. First check whether a field the record already carries can answer the new question, because a second ADR for one field is the bloat the operator reads as complexity: a free-text decision can hold the label outcome, and an enumerated field list is the case that needs the override ADR. Give a failed write its own decision value rather than a note on a successful one.
